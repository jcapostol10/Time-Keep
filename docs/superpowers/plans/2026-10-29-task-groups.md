# Tasks by group — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A workspace can show tasks by group: a task belongs to one or more user groups, and when the new "Task visibility" setting is "By group", members see and track only the tasks of their groups, must pick one on a project that has them, and every write path refuses any other task.

**Architecture:**
- **Departments are the existing groups** (`user_group`, `user_group_member`). One new join table, `task_group`, mirrors `project_group`; one new column, `workspace_settings.task_visibility`, switches the rule on. `task_assignee` and `task_creators` stay in the schema, unread (expand only; contraction is a later migration).
- **One read, one write.** Every member-facing task list comes from `visibleTasksFor()` in `apps/web/src/server/catalog/tasks.ts`, which applies rules 3, 6 and 7 in SQL. Every entry write already passes through `assertDetailsUsable()` in `apps/web/src/server/time-entries.ts`; it gains the `task.trackTime` check and rule 8, evaluated against the entry owner's actor (`EntryScope` is the owner's viewer), so add-for-others, bulk edit and import follow rule 11 without new code.
- **The matrix answers who.** `task.create` and the new `task.assignGroups` are owner, admin and the project's managers; the new `task.trackTime` reads the setting, the actor's `groupIds` and the task's groups. The "Who can create" setting loses tasks.
- **EVERYONE is today.** With the default setting nothing changes: `visibleTasksFor` returns every active task, `task.trackTime` is always true, and no extra query runs.

**Tech Stack:** Next.js 16 App Router, React 19, Drizzle/Postgres, zod 4, react-query, Vitest, Playwright. No new dependencies.

**Spec:** the owner's change request of 2026-10-29 ("tasks by group", rules 1–11 and steps 1–8), recorded as decision 11 of `docs/superpowers/specs/2026-10-27-phase-4-design.md` by Task 1. Phases 4a and 4b are merged (`main` = `5654566`, tag `phase-4`); this plan is written against that code. Branch: `feat/task-groups`.

## Global Constraints

- **Rule 1:** everything below applies only when `task_visibility = BY_GROUP`. With `EVERYONE` (the default) every existing unit, integration and e2e test passes unchanged, except the two tests Task 2 rewrites because the assignee UI is hidden.
- **Invariant 3:** every action and route handler calls `requireWorkspaceAccess` then `authorize` (or a helper listed in `authorize-coverage.test.ts`); 403 for a role or setting, 404 for a resource outside the actor's scope.
- **Entry writes** go only through `apps/web/src/server/time-entries.ts`; **task rows for member-facing lists** come only from `apps/web/src/server/catalog/tasks.ts` (Task 4 adds the test).
- **Rule 10:** existing entries are never changed; unchanged details are not re-checked. The refusal text is exactly `This task isn't available to your groups.`
- **Rule 11:** checks run against the entry owner's groups, never the actor's.
- **Migration `0012_task_groups`** is additive (one enum type, one column with a constant default, one table with `.enableRLS()`), applied to the shared database with the **Migrate shared database** workflow before the branch's first preview.
- **UI copy:** the word is "Groups" everywhere; never "department". Setting label "Task visibility", options "Everyone" and "By group".
- **e2e:** new lines go in `docs/E2E_COVERAGE.md` unticked, failing specs come before app code, a line is ticked only after its test was seen failing with the behaviour broken, fixtures from `e2e/fixtures.ts`, demo accounts only for role and isolation tests, the suite stays under 10 minutes on a preview (Task 8 says what to do if it does not).
- **Rulings** (the plan's calls where the request leaves a choice; each is also in the owner's approval message):
  - R1. Rule 8 binds where decision 5 binds: on Stop and every save, never on Start, and only for an entry owner whose role is manager or member (owners and admins see every task, so no task is forced on them). It reuses the required-field plumbing: `Task is required.` with `field: "task"`.
  - R2. In BY_GROUP mode a task is never created without a group: the new-task dialog, `createTask` and the import's "Groups for new tasks" require one, and the picker's inline "Create task" shows only in EVERYONE mode (to people with `task.create` on that project). Tasks created before the switch, or whose groups were removed or deleted, are the "No group" case of rule 7.
  - R3. `task.trackTime` is checked in `assertDetailsUsable`, so it runs exactly where a task is chosen or changed (start, manual, edit, duplicate, continue, bulk edit, import, timesheet and calendar saves) and never on a stop, a time edit or a split. A crafted task id fails there with rule 10's text (an `INVALID` error), on every path.
  - R4. `Actor.groupIds` is loaded only in BY_GROUP mode, so EVERYONE costs no extra query.
  - R5. `docs/PERMISSIONS.md` regenerates in Task 3 with the matrix, not in Task 1: it is generated from code and `permissions-doc.test.ts` fails while the file and the code disagree.
  - R6. The Team page has no group or member detail view, so "Tasks" (group) and "Tasks available" (member) are dialogs opened from the existing row menus, fed by one admin-only JSON route.
  - R7. `workspace_settings.task_creators` and `task_assignee` stay (expand only); the settings schema and form drop `taskCreators`; `taskInputSchema` keeps `assigneeIds` so nothing else breaks. Dropping both is a backlog item for a later contract migration.
  - R8. Demo seed assignments are chosen so the demo-tenant specs keep passing: member2 keeps seeing "Internal" and not "Mobile app"; member1 keeps seeing "Mobile app › iOS"; the manager joins Engineering so their picker still lists "Website redesign"; the Design group stays member1 + member2 (reports.spec reads it).
  - R9. The perf seed gains groups and tasks in BY_GROUP mode so the member's picker query is timed with the Summary.

## Review Focus

1. **A task whose last group is deleted or whose group loses the member mid-timer:** the running timer still stops (rule 10), the entry row keeps showing the task, Continue and Duplicate are refused with rule 10's text. Tests: Task 5 ("a running timer on a task that became unavailable still stops"), Task 8 e2e.
2. **Rule 8 against hidden tasks:** a project whose only active tasks are invisible to the member is absent from their picker, and a manual entry naming that project with no task is refused with `Task is required.`; a project with no tasks at all behaves as today. Test: Task 4 ("rule 8 hides a project whose tasks the member cannot see") and Task 5.
3. **Add-for-others crosses groups:** an admin in no group adds time for a member on the member's group's task (allowed) and on a task outside the member's groups (refused), and a manager outside the member's groups cannot pick their own groups' tasks for the member. Test: Task 5 ("add-for-others checks the owner's groups, not the actor's").
4. **The switch itself:** turning BY_GROUP on with every task grouped (count 0), with 3 ungrouped (count 3), and turning it off again restores every picker. Tests: Task 4 (`countTasksWithoutGroup`), Task 7 e2e.
5. **Private project plus rule 9:** assigning a group to a task on a private project adds the group's access in the same transaction and the Access tab shows it; removing the last task of that group keeps the access; a group deleted from the Team page takes its task rows with it (cascade) and the task shows "No group". Test: Task 4 ("assigning a group to a task on a private project grants the group access").
