# Phase 5c — Kiosk and limited users: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- Admins create kiosks: a device URL that needs no login, a default project and task, the people allowed, a session timeout, the logo, and (Pro) a photo at clock in.
- On the kiosk a person picks their name and enters their PIN, or scans their QR code, then clocks in, starts or ends a break, or clocks out. Every punch is a normal entry written through the entry service with the server's time, so locks, approvals, force timer and required fields apply.
- People set their PIN and print their QR code on their profile; admins add limited users (kiosk only, no email login), set their PIN, and convert them to normal members.

**Architecture:**
- **Pure rules in core**: `kiosk.ts` holds the throttle maths (`throttleUntil`), the punch state machine (`kioskState`, `kioskActions`), the QR payload format and the kiosk copy. The matrix gains `kiosk.manage`, `pin.setOwn` and `member.manageLimited`; `planAllows` gains `"kioskPhoto"`.
- **Services** live in `apps/web/src/server/kiosk/`. `kiosks.ts` is admin CRUD and the token. `credentials.ts` covers PIN and QR. `runtime.ts` covers resolve, people, identify, punch and today's work. `photos.ts` stores and purges photos. `server/limited-users.ts` holds create and convert.
- **The device side is one route family**, `/api/kiosk/[token]/…`, authorized by the kiosk token (`resolveKiosk`), never by a session. Identify returns a signed, short-lived punch ticket, so the PIN is checked once per visit.
- **A punch is `startTimer` / `stopTimer`** with the person's own viewer (`loadViewer`): clock in starts work with the kiosk defaults; start break starts a `break` entry, which stops work in the same transaction; end break starts work again; clock out stops the running entry.

**Tech Stack:** Next.js 16 App Router, React 19, Drizzle/Postgres, zod 4, react-query, Vitest, Playwright. Two new dependencies in `apps/web`: `qrcode@1.5.4` (MIT; draws the profile QR and the e2e camera stream) with `@types/qrcode`, and `jsqr@1.4.0` (Apache-2.0; decodes camera frames on the kiosk). Both go in `docs/THIRD_PARTY.md`.

**Spec:** `docs/superpowers/specs/2026-10-31-phase-5-design.md`: decisions 15–20, Part 6, migration `0015_phase5c`, the kiosk lines of Tests and Risks. Builds on 5a/5b (`time-entries.ts` writers, `assertWritable`, `loadViewer`, `outbox` `isUndeliverable`, `daily-jobs.ts`, `storage.ts` private bucket, `share-links.ts` token pattern).

## Global Constraints

- **Decision 15:** the kiosk token is `randomBytes(32).toString("base64url")`; only its sha256 is stored (as `share-links.ts`). Unknown, rotated or disabled: the same 404 ("This kiosk is not available."). Opening the kiosk sets no cookie and reads no session.
- **Ruling R1 (the spec says "copy the device URL" but stores only the hash):** the URL is shown, with Copy, when the kiosk is created and after Rotate, never again; a lost URL means Rotate. *Cost if wrong:* a second device on the same kiosk needs the URL kept by the admin.
- **Decision 16:** a PIN is 4–6 digits, hashed with `hashPassword` / `verifyPassword` from `better-auth/crypto`, per (workspace, user). A QR token is 32 random bytes (sha256 stored, unique). The QR payload is `tkq1.<token>`; anything else is ignored without counting as a failure.
- **Throttles:**
  - 5 wrong PINs for one person on one kiosk within 15 minutes lock that person on that kiosk for 15 minutes from the fifth failure. Only failures since the person's last success count.
  - 30 failures (PIN or QR) on one kiosk within 15 minutes lock that kiosk's PIN entry for 15 minutes. QR scanning stays open.
  - Every attempt is a `kiosk_attempt` row. A refused attempt while locked is not recorded.
  - Verification runs under `pg_advisory_xact_lock(hashtext('kiosk:' || kiosk_id || ':' || user_id))`.
- **Ruling R2 (rate limiting, decision 15):** the throttles are the rate limit; successful punches are never limited, because a shift change is many people at once.
- **Ruling R3 (punch ticket):** identify returns `ticket = base64url(json { k: kioskId, u: userId, r: tokenRotatedAt ms, e: exp ms }) + "." + base64url(HMAC-SHA256)`. The HMAC key is `sha256("kiosk-ticket:" + BETTER_AUTH_SECRET)`. The ticket lives 120 s. A punch re-checks it with `timingSafeEqual`, then checks that the kiosk is active with the same `r`, and that the person is an ACTIVE member who is still allowed. Otherwise 404.
- **Decision 17:** clock in is `startTimer` with description `Kiosk: <kiosk name>`, the kiosk's default project and task, and `billable` from that project's default. Start break is `startTimer({ type: "break" })` and needs `allow_breaks`; with it off, no Break button and a 409. End break is `startTimer` with the kiosk defaults. Clock out is `stopTimer` on the running entry. The server's `now` is the only clock. An action that does not fit the person's state is a 409 carrying the fresh state.
- **Decision 18:** a limited user is a direct `user` insert (never Better Auth, so no personal workspace) with email `limited+<id>@kiosk.invalid`, `emailVerified false`, no `account` row, and `membership.limited = true`, role `member`.
  - Better Auth's `sendMagicLink` and `sendResetPassword` send nothing to an undeliverable address (`isUndeliverable`).
  - Converting a limited user replaces the email in place (same id), sets `limited = false`, and asks Better Auth for a reset-password link to the new address.
  - An address that already has a user is refused: "This address already has an account; invite it instead."
- **Ruling R4 (the spec says the set-password email goes through the outbox):** the conversion email is Better Auth's reset email, sent in the request like every other auth email (CLAUDE.md). `emailAndPassword.onPasswordReset` sets `emailVerified = true`, because the link proved the address. *Cost if wrong:* if SMTP fails, the admin sees the error; the person can still use "Forgot password".
- **Decision 19 + Ruling R5:**
  - The photo option is offered only when `planAllows(ws, "kioskPhoto")` (always true today).
  - The kiosk shows "This kiosk takes a photo when you clock in." before the camera starts. If the camera is unavailable, clock in goes ahead without a photo.
  - The photo is a JPEG (magic bytes `FF D8 FF`, at most 1 MiB), stored with `uploadExport` under `kiosk-photos/<workspaceId>/<entryId>.jpg`, plus a `kiosk_photo` row.
  - Photos are deleted after 90 days, and attempts after 1 day, by `runDailyJobs` for every workspace.
- **Ruling R6 (where admins see the photo):** Detailed report rows carry `photo: boolean` only for viewers with `kiosk.manage`. A camera button opens `/api/w/[slug]/kiosk-photos/[entryId]`, a 302 to a 5-minute presigned URL; 404 for anyone else.
- **Ruling R7 (who is listed):** the kiosk lists its allowed, ACTIVE members, by name, with avatars (everyone, or its users and groups). Someone with no PIN who taps their name sees "No PIN set. Set one in your profile, or ask an admin."
- **Ruling R8 (profile scope; a PIN is per workspace):** Profile → Kiosk lists the person's workspaces that have an active kiosk allowing them. Each has Set PIN / Change PIN, Show QR code (created on first show) with Print, and Rotate QR code. No such workspace: the section is hidden. Admins set a limited user's PIN and show or rotate their QR code from the Team row menu.
- **Ruling R9 (the shared database):** `e2eOnlyWorkspaceIds` counts a limited member (`membership.limited`) as an e2e member, and `cleanupE2eData` then deletes `@kiosk.invalid` users left with no membership. Otherwise every e2e kiosk test would leave a workspace behind on Supabase.
- **Matrix (decision 20):**
  - `kiosk.manage`: ADMINS.
  - `pin.setOwn`: own for every role (on `{ kind: "person", userId }`).
  - `member.manageLimited`: ADMINS. Covers create, convert, a limited user's PIN and QR.
  - `SECTION_TITLES.kiosk = "Kiosks"`.
  - `authorize-coverage.test.ts` covers the new `/api/w` routes and actions. A new `kiosk-coverage.test.ts` fails when an exported handler under `app/api/kiosk` does not call `resolveKiosk(`.
- **Copy:**
  - Buttons: "Clock in", "Start break", "End break", "Clock out", "Enter your PIN", "Scan QR code".
  - Messages: "Wrong PIN.", "Too many wrong PINs. Try again in 15 minutes.", "PIN entry is paused for 15 minutes. Scan your QR code instead.", "This QR code is not valid on this kiosk.", "Worked today: <h:mm>".
  - Team page: "Kiosk only", "Add limited user", "Convert to member".
  - PIN setup note: "Five wrong tries lock your PIN for 15 minutes. A 6-digit PIN is harder to guess."
- **Defaults:** session timeout 15 s (5–300). Show logo on, photo off.
- **Migration `0015_phase5c`** is additive: new enum `kiosk_attempt_method (PIN, QR)`, the tables with `.enableRLS()`, `membership.limited boolean not null default false`. It is applied through the Migrate shared database workflow before the preview.
- **e2e:** `docs/E2E_COVERAGE.md` lines go in unticked, with specs failing before UI code. Tick only after seeing each fail with its guard broken. `kiosk.spec.ts` runs on previews (the acceptance punch and 375 px); `kiosk-extra.spec.ts` is `@nightly`. The preview run was 10.1 min after 5b; if it grows, move specs to nightly rather than adding to previews.

## Review Focus

1. **A punch into submitted or locked time**: with the person's current week PENDING, Clock in answers "This week is submitted for approval.", writes nothing, and the screen shows the message. Test: Task 4.
2. **A kiosk rotated or disabled mid-visit**: a ticket from before Rotate or Disable is refused with 404, and the screen goes back to "This kiosk is not available." Test: Task 4 (runtime) and Task 3 (rotate changes `token_rotated_at`).
3. **A person who stops being allowed between identify and punch** (removed from the kiosk's group, deactivated, removed): the punch is a 404 and nothing is written. Test: Task 4.
4. **Concurrent wrong PINs**: ten parallel wrong PINs for one person record at most five failures, and the sixth onwards answer "Too many wrong PINs." Test: Task 4 (two handles, `Promise.all`).
5. **A person whose timezone differs from the workspace's**: "Worked today" for someone in Asia/Manila on a New York workspace sums their own Manila day, including the running entry up to now. Test: Task 4.
