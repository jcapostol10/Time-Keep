# Phase 4a — Permissions, team and rates: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- One `can(actor, action, resource)` that every server action, route handler and hideable page asks.
- Managers scoped to the people and projects they manage.
- User groups.
- A Team page that runs a real team: bulk invite, CSV import, roles, deactivate, remove, ownership transfer, manager scope.
- A five-level billable rate hierarchy with history, rated onto each entry, and an "apply to past entries" job with progress.
- Amounts in reports, the dashboard, exports and share links.

**Architecture:**
- **The matrix:** a typed table in `packages/core/src/permissions.ts` (pure). `apps/web/src/server/authz.ts` turns a request into an `Actor` (role plus manager scope, two indexed queries, cached per request), enforces the matrix and hands the report engine one SQL scope condition.
- **Rates:** rows with `effective_from`. A single SQL resolution, in `packages/db/src/rates-sql.ts` so the seed can use it too, rates entries inside `time-entries.ts`. A batch job (`after()`, resumable by cursor) re-rates past entries.
- **Amounts:** stored on the entry in integer minor units. Reports sum them.

**Tech Stack:** Next.js 16 App Router, React 19, Drizzle/Postgres, zod 4, react-query, Better Auth 1.7.7 organization plugin (`afterAcceptInvitation` hook), Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-27-phase-4-design.md`: Parts 1–3, decisions 1–4 and 9–15. The owner agreed to decisions 1, 2, 4, 9 and 10 on 2026-10-27. Decision 3 was revised that day to the industry rule (Clockify, Harvest, Toggl), as the owner asked.

## Global Constraints

- **Invariant 3:** every query is scoped by `workspaceId`.
  - Actions and route handlers call `requireWorkspaceAccess` (membership), then `authorize(ctx, action, resource)`.
  - A role that may never act gets 403.
  - A resource outside the actor's scope (an entry, a private project, a member outside a manager's team) gets 404.
- **Invariant 2:** money is integer minor units plus an ISO 4217 code.
  - Parse strings with integer maths (never `parseFloat`).
  - SQL sums are `::bigint` with `.mapWith(Number)`.
  - `amount = round_half_up(rate × seconds / 3600)` per entry.
- **Invariant 5 and decision 3:** a rate change never re-rates saved entries unless the person chooses "Entries from a date" or "All entries".
  - A new entry takes the rate in force at its start.
  - An edit keeps the rate and recomputes the amount.
  - Only a change of project, task, person, or billable switched on re-rates.
- **Rate precedence, most specific first:** task → project_member → project → member → workspace. A `null` amount row means "no rate at this level from this date".
- **Who sees what:**
  - Owners and admins see everything and are the only ones who set rates.
  - Managers read time and amounts in their scope (managed people directly or through groups, plus entries on managed projects, plus their own), and edit the projects they manage.
  - A manager with no assignments reads only their own time.
  - Members see their own time and never amounts.
- **Entry writes** go only through `apps/web/src/server/time-entries.ts`. The only other writer is the rate job's batch `UPDATE` through `rates-sql.ts`. The seed uses the same SQL.
- **Migration `0010_phase4a`** is additive only. Every new table has `.enableRLS()` (`rls.test.ts`). The branch runs the "Migrate shared database" workflow before its preview e2e.
- **Better Auth** still owns invitations (create, cancel, accept). Role, status, removal and ownership are written by `server/team.ts` directly, after `authorize`.
- **e2e:**
  - New lines go in `docs/E2E_COVERAGE.md` (unticked) and failing specs come before app code.
  - Tick a line only after its test was seen failing with the behaviour broken.
  - Fixtures come from `e2e/fixtures.ts`.
  - Demo users only for role and isolation tests.
  - The suite stays under 10 minutes on a preview.
- **375 px and dark mode:** the Team page and the rate dialog work at 375 px. Money is formatted by `formatMoney` (`Intl.NumberFormat`).

## Review Focus

1. **A manager tampering with URLs or ids:**
   - `userIds=` of someone outside scope in a report or export;
   - `updateEntryAction` with another person's entry id;
   - a project page of an unmanaged project.

   All of these must show scope-only data or a 404, never a 403 that confirms existence. Tests: Task 3 (engine), Task 4 (actions and pages).
2. **Money typed by people:** `1,250.50`, `1250.5`, `0`, `12.345` in USD (refused: too many decimals), `1000.5` in JPY (refused), `-5`, an empty field, a value over 1,000,000 an hour (refused). Test: Task 7.
3. **A rate's effective day in the workspace timezone:** an entry starting 00:30 Manila on the effective date gets the new rate; one at 23:59 the day before gets the old. Core and SQL agree. Tests: Tasks 7 and 8.
4. **Locking yourself or the owner out:**
   - deactivating, removing or demoting the owner;
   - an admin deactivating or removing themselves;
   - deactivating someone with a running timer (it stops at the deactivation time).

   Test: Task 5.
5. **The recalculation job under pressure:**
   - killed mid-run, then retried, resumes from its cursor;
   - two rate changes a second apart merge into one queued job from the earlier date;
   - an entry edited during the job ends with the same amount a fresh resolution gives.

   Test: Task 9.

### Task 9: The "apply to past entries" job and the currency relabel

**Files:**
- Create: `apps/web/src/server/rate-recalc.ts` and `rate-recalc.test.ts`, and `apps/web/src/app/api/w/[workspaceSlug]/rate-recalc/route.ts` (GET the latest job).

  - `apps/web/src/server/actions/workspaces.ts`: a currency change relabels;
  - `packages/core/src/schemas.ts`: `confirmCurrencyChange: boolean` on the settings schema.

**Interfaces:**
- `requestRateRecalc(db, workspaceId, userId, from): Promise<{ jobId: string; merged: boolean }>`. If a `queued` job exists, it lowers that job's `from` to the earlier date and returns it (`merged: true`). Otherwise it inserts a `queued` row.
- `runRateRecalcJob(db, jobId, opts?: { batchSize?: number; now?: Date }): Promise<void>`:
  1. It claims the job: `queued` → `running`, sets `started_at`, and counts `total` (live entries with `start >= from`).
  2. It loops batches of `batchSize` (default 5,000) by keyset `(start, id) > (cursor_start, cursor_id)`. Each batch is one transaction: `rateEntriesWhere(id IN batch)` and update `processed` and the cursor.
  3. It finishes `done`, then claims the next `queued` job of the workspace in the same call.
  4. On an error it marks the job `failed` with the message.
- `retryRateRecalc(db, ctx, jobId)`: `failed` → `queued`, keeping the cursor.
- `expireRateRecalcJobs(db, now)`: marks a job `running` with `started_at` over 15 minutes old as `failed` ("Timed out; Retry continues where it stopped"). It runs at the start of `runRateRecalcJob`.
- `latestRateRecalc(db, workspaceId): RateRecalcDTO | null`, where `RateRecalcDTO = { id; status; from: string; total: number | null; processed: number; error: string | null }`.
- Currency relabel: inside the settings transaction, `UPDATE rate SET currency` and `UPDATE time_entry SET rate_currency` for the workspace. The action refuses without `confirmCurrencyChange` when any rate exists, returning a field error the form turns into a confirmation.
