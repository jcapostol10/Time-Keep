# Phase 5a — Approvals, locks and the email outbox: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- Members submit a period of their time; approvers approve or reject it (with a note), in bulk, from an Approvals page; approved and pending time is read-only for its owner, and owners and admins change it only with a note that is logged.
- Admins lock time before a fixed date or older than N days; the server refuses non-admins' writes there.
- Every email the phase sends goes through an outbox written in the same transaction as its cause, drained right after the request and by one daily cron run, which also sends the weekly "unsubmitted period" reminder.

**Architecture:**
- **Pure rules in core** (`packages/core/src/approvals.ts`): period maths in the workspace timezone, the lock boundary, the request state machine, and which period an entry belongs to. The permission matrix gains the approval actions.
- **One guard in the entry service**: `assertWritable` (in `apps/web/src/server/entry-guard.ts`, called only from `time-entries.ts`) applies the lock and the approval state to every write path, and logs owners' and admins' edits of submitted time with their note. A static test fails when an exported writer in `time-entries.ts` does not call it.
- **Approval service** (`server/approvals.ts`): submit, withdraw, review, reopen, the lists the page reads; it enqueues email through `server/outbox.ts` in its own transaction.
- **Outbox and daily job**: `email_outbox` rows drained by `drainOutbox` (`FOR UPDATE SKIP LOCKED`), called by `after()` in the actions, by `/api/cron/daily` (Vercel Cron, `CRON_SECRET`) with `runDailyJobs`, and locally by the pg-boss worker through `/api/cron/outbox`.

**Tech Stack:** Next.js 16 App Router, React 19, Drizzle/Postgres, zod 4, react-query, Vitest, Playwright, pg-boss (worker only). No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-31-phase-5-design.md`: decisions 1–7 and 20, Parts 1–2, and migration `0013_phase5a`.

## Global Constraints

- **Invariant 3:** every new action and `/api/w` route calls `requireWorkspaceAccess` then `authorize`; cron and test routes are guarded by their secret and answer 404 without it.
- **Entry writes** go only through `apps/web/src/server/time-entries.ts`; `assertWritable` is called from there and nowhere else.
- **Decision 2:** periods (WEEKLY from the workspace week start, SEMI_MONTHLY 1–15 / 16–end, MONTHLY) and lock dates are in the **workspace** timezone; an entry belongs to the period containing its start. Requests never overlap.
- **Decision 4:** approvers are ADMINS (default) | TEAM_MANAGERS | PROJECT_MANAGERS, each including the previous; managers and members never approve their own; owners and admins may.
- **Decision 5:** PENDING or APPROVED time is read-only for its owner and for managers; owners and admins change it only with a note (`NOTE_REQUIRED` otherwise), logged as `ADMIN_EDIT`.
- **Decision 6:** non-admins cannot write entries whose start (before or after the change) is before the lock; stopping a running timer is always allowed; owners and admins are never locked and never asked for a note by a lock alone.
- **Rule from Phase 4 design decision 3:** the rate recalculation skips entries in APPROVED periods.
- **Decision 1:** an email is enqueued in the same transaction as its cause; nothing is sent inside a request; `.invalid` addresses are skipped.
- **Copy:** "Submit for approval", "Withdraw", "Resubmit", "Approve", "Reject", "Reopen"; refusals "This period is submitted for approval." and "This period is approved." and "Entries before <date> are locked."
- **Migration `0013_phase5a`** is additive (enums, columns with constant defaults, new tables with `.enableRLS()`), applied to the shared database through the Migrate shared database workflow before the preview.
- **Defaults reproduce today:** approval off, lock off; with both off no write path changes behaviour and every existing test passes unchanged.
- **e2e:** lines in `docs/E2E_COVERAGE.md` unticked and failing specs before app code; tick only after seeing each fail with its guard broken; run `pnpm format:check` with the gate.

## Review Focus

1. **A period's boundary across timezones**: an entry at 23:30 Sunday in Manila belongs to the week that starts Monday in New York for a New York workspace; the guard and the Submit control agree. Test: Task 1 (core) and Task 4 (guard).
2. **A timer running in a period being submitted**: submit is refused ("Stop the timer before submitting this period.") and the running timer can still be stopped after the period is approved. Test: Task 5.
3. **Concurrent submit and edit**: a member's edit and their own submit at the same moment never leave an edited entry in an approved period; both take the person's timer lock. Test: Task 5 (`submitPeriod` and `updateEntry` under `timerLock`).
4. **Two drainers**: two concurrent `drainOutbox` calls send each email once; a send failure retries with backoff and gives up after five attempts. Test: Task 3.
5. **Settings changes with requests in flight**: changing the period type while a request is PENDING is refused; turning approval off withdraws pending requests (logged) and keeps APPROVED periods read-only. Test: Task 8.
