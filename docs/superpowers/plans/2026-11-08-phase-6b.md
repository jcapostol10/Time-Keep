# Phase 6b — Estimates, budgets and alerts: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A project carries one estimate, by time or by money, for the whole project or per calendar month; everyone allowed to see it watches a progress bar fill wherever the project shows, and the daily job emails the people in charge once per threshold crossed.

**Architecture:** Five columns on `project`, one on `task`, one on `workspace_settings`; no new table. Progress is computed by one aggregate (`progressFor`) over raw, stopped work entries of the current period, never stored and never rounded; who sees it is one core rule (`progressVisible`). The alerts are the target-email mechanism: evaluated by `runDailyJobs`, sent through the outbox under a `kind` that names the project, threshold and period.

**Tech stack:** Drizzle + Postgres (migration `0017_phase6b`), `packages/core` pure maths (Vitest), Next.js 16 server actions, recharts for the Budget chart, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-05-phase-6-design.md` (decisions 10–13, Data model "Migration 0017_phase6b", Access rules, Tests).

## Global constraints

- Money is integer minor units + ISO 4217; never floats. A money estimate is in the **project's currency** (`projectCurrency` from `server/rates.ts`); amounts in another currency are left out of it, never converted.
- A time estimate measures **all work time** on the project, billable or not; a money estimate the **billable amount**. **Raw time: report rounding never applies.** Breaks never count. Only stopped, live (`deleted_at is null`) entries count, as in reports.
- Periods are **calendar months in the workspace timezone** (`monthBoundsInZone`); an entry belongs to the month of its start. Period keys: `all` for a whole-project estimate, `YYYY-MM` for a monthly one.
- **Progress is computed, never stored.** One aggregate for every place a bar shows: projects table, project header, dashboard top project, Summary rows grouped by project, the Budget tab. Not in pickers or entry rows.
- Who sees progress (`progressVisible`): anyone with `project.update` on the project (owners, admins, the project's managers); otherwise a time bar only when "members see the team's time" is on, and a money bar never. Share links never carry progress.
- Tasks carry an optional time estimate shown on the Tasks tab; they never add up into the project's.
- Alerts: thresholds are a workspace setting, default `[50, 80, 100]`, up to five integers from 1 to 200, stored sorted without duplicates. Each fires **once per project, threshold and period**: outbox `kind` `budget:<projectId>:<threshold>:<periodKey>`. Recipients: active owners and admins, and the project's managers. Archived projects, templates and projects with alerts off send nothing.
- Date maths only via `packages/core` (`monthBoundsInZone`, `localDateKey`, `addDaysInZone`); never `n * 86_400_000`.
- `time_entry` stays written only by `server/time-entries.ts` and `rates-sql.ts` (this phase reads it only).
- The migration is additive; previews never migrate: **stop after Task 2**, push, and ask the owner to run the Migrate shared database workflow on the branch.
- Tests first. E2E: unticked lines in `docs/E2E_COVERAGE.md` and a failing spec before UI code; a line is ticked only after its test was seen to fail with the behaviour broken, and the commit message records the break.
- The preview lane stays under 9 minutes: Task 6 measures it with `--reporter=list` and moves a mature spec to `@nightly` if needed.
- Commits end with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`. Merging and pushing `main` need the owner's approval; the branch is deleted once merged.

## Review focus

1. Entries around local midnight on the last day of a month in Manila (UTC+8) vs UTC: a monthly estimate counts them in the right month and the period key follows the workspace timezone, not the server's (Task 1 and Task 2 tests).
2. A project billed in EUR with a money estimate and some entries rated in USD (a member rate before the client's currency was set): the bar reads EUR, the USD amounts are left out and the label names the currency (Task 2 test).
3. A member on the Projects page: no bar at all with the team-time setting off, time bars but never money bars with it on; an admin sees both (Task 3 test, e2e test 5).
4. The daily job run twice the same day, then once after the estimate is raised: the first run sends one email per crossed threshold and recipient, the second nothing, the third nothing new for that period; a new month restarts (Task 4 tests).
5. Estimate inputs at the edges: `0`, a negative, `abc`, a monthly money estimate on a project without rates (the bar shows 0% and the tab says the project has no rates); thresholds typed as `80, 50, 50, 250` → saved `[50, 80]`, the 250 refused with a message (Tasks 1, 3 and 5).
