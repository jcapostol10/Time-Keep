# Phase 5b — Time off, holidays, attendance and targets: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:**
- People request time off against policies (days or hours; none, yearly or monthly grants); approvers approve or reject it under the approvers setting; balances are computed, never stored; approved time off shows on the Calendar, the Timesheet and a Time off page, never in time reports.
- Admins keep holidays for any country: imported from a bundled dataset after a review, or added by hand, for the whole workspace or for users and groups.
- Each member has a capacity (daily hours, weekly hours, working days); a fifth report tab, Attendance, shows each person's day (first in, last out, work, breaks, time off, overtime, undertime) and exports to CSV, Excel and PDF.
- Target rules remind people who tracked too little and alert managers about too much, from the daily job, through the outbox.

**Architecture:**
- **Pure maths in core**: `time-off.ts` (day counting, balances, minutes per day), `holidays.ts` (which holidays apply on which dates, yearly repeats), `attendance.ts` (per-day and per-week capacity, overtime, undertime), `targets.ts` (rule evaluation). The dataset import is a separate subpath, `@timekeep/core/holiday-import` (wraps `date-holidays`), imported by server code only so the data never reaches a client bundle.
- **Services** in `apps/web/src/server/time-off/*` (policies, holidays, requests, balances) and `server/attendance.ts`, `server/targets.ts`; every write is an action through `authorize`; emails go through `enqueueEmail` in the same transaction and `drainSoon()` after.
- **Attendance reads the entry table the way the report engine does** (stopped, live work and break entries, raw durations), with the people scope of the new `attendance.read` rule; exports reuse the column-record pipeline and the PDF template.
- **The daily job** (`runDailyJobs`) gains target reminders and alerts, evaluated on the previous local day in each workspace's timezone.

**Tech Stack:** Next.js 16 App Router, React 19, Drizzle/Postgres, zod 4, react-query, Vitest, Playwright. One new dependency: `date-holidays@3.38.0` (ISC code, CC-BY-3.0 data: attribution required, shown in the import dialog and `docs/THIRD_PARTY.md`).

**Spec:** `docs/superpowers/specs/2026-10-31-phase-5-design.md`: decisions 8–14 and 20, Parts 3–5, migration `0014_phase5b`. Builds on 5a (`server/approvals.ts` `approversFor`, `server/outbox.ts`, `server/daily-jobs.ts`).

## Global Constraints

- **Invariant 3:** every new action and `/api/w` route calls `requireWorkspaceAccess` then `authorize`; `authorize-coverage.test.ts` must pass with them; outside-scope reads are 404.
- **Decision 8:** time off is never a `time_entry`, never in Summary, Detailed, Weekly or the dashboard, never rated.
- **Decision 9:** balances are computed. **Ruling R1 (spec silent on the year):** every policy reckons in the calendar year of the workspace timezone: YEARLY grants the allowance on 1 January; MONTHLY grants allowance ÷ 12 on the 1st of each month on or after the later of the person's join date and the policy assignment date; requests and adjustments count in the year of their start date; nothing carries over. NONE: adjustments only; "Unlimited" when it also allows a negative balance. PENDING never reduces the balance, but counts in the "would go negative" check.
- **Amounts are integer hundredths** of the policy's unit (`amount_centi`: 150 = 1.5 days or 1.5 hours); MONTHLY's month *m* total is `round_half_up(allowance_centi × m / 12)`, so twelve months sum to the allowance exactly. Never floats in the database.
- **Decision 10:** a DAYS request counts the person's working days in the range minus holidays that apply to them; a half day (0.5) only on a one-day request. An HOURS request is minutes per day for one day, or a total for a range. A request spans one calendar year at most (**Ruling R2**) and never overlaps the person's PENDING or APPROVED request ("This overlaps your time off on 3–5 Mar.").
- **Decision 11:** nothing in the code is specific to a country; the country defaults from the workspace timezone (`Asia/Manila` → PH) through the dataset's own timezone list; only `public` days by default, "Include optional days and observances" adds `optional`, `observance` and `bank` (never `school`); an import never adds a row with the same date and name as an existing one; Islamic-calendar dates (rules naming Muharram, Safar, Rabi, Jumada, Rajab, Sha'ban, Ramadan, Shawwal or Dhu al-) are imported with `estimated = true` and shown with "Estimated: confirm the proclaimed date".
- **Decision 12 + Ruling R3:** time off review uses `approval.review`'s rule with no projects (`{ kind: "approval", userId, projectIds: [] }`), so at PROJECT_MANAGERS a project manager reviews time off only for people they manage; managers never review their own; a policy without approval approves on submit; cancelling an approved request is a reviewer's action with a note; rejection needs a note.
- **Decision 13 + Ruling R4:** attendance days are each person's own (`user.timezone` → workspace timezone); work and breaks are raw (rounding never applies); capacity = daily minutes on a working day, 0 on a non-working day or an applicable holiday, minus time off that day (a full day off = the daily capacity, a half day = half). Weekly overtime is against weekly minutes minus that week's time off and holiday capacity. People in scope: owners and admins everyone; a manager themselves and the people they manage (not people seen only through managed projects, whose days would be partial); a member themselves.
- **Decision 14:** UNDER rules email the person (unless `user_settings.mute_target_reminders`); OVER rules email the workspace's active owners and admins and the person's managers, never muted; daily rules evaluate yesterday's working days that are not holidays or full days off; weekly rules evaluate last week on the first day of the week; each email is sent once per (rule, person, day or week) through the outbox row's `kind = "target:<ruleId>:<userId>:<dateKey>"`.
- **Copy:** "Request time off", "Withdraw", "Approve", "Reject", "Cancel time off", "Import public holidays", "Include optional days and observances", "Unlimited", "Time off: <policy>", "Mute target reminders"; refusals "This would take <policy> below zero.", "A half day is for a one-day request.", "Time off cannot span two years: split the request.".
- **Migration `0014_phase5b`** is additive: new enums and tables with `.enableRLS()`, `membership` columns with constant defaults, `ALTER TYPE export_report ADD VALUE 'attendance'`; applied to the shared database through the Migrate shared database workflow before the preview.
- **Defaults reproduce today:** no policies, no holidays, no target rules, capacity 8 h / 40 h / Mon–Fri; every existing test passes unchanged.
- **e2e:** lines in `docs/E2E_COVERAGE.md` unticked and failing specs before UI code; tick only after seeing each fail with its guard broken. The preview run was 9.3 min in 5a: `time-off.spec.ts` runs on previews (acceptance checks), `attendance.spec.ts` is `@nightly`.

## Review Focus

1. **A holiday or day off inside a DAYS request**: Mon–Fri with a Wednesday holiday counts 4 days, and a weekend inside a range counts nothing; a person with Sun–Thu working days counts their own week. Test: Task 1 (`countRequestCenti`) and Task 5 (a request over a group-assigned holiday counts it only for members of the group).
2. **Balance at a year edge**: a request on 31 Dec counts in that year; one from 30 Dec to 2 Jan is refused (R2); MONTHLY for someone who joined on 15 Oct shows Nov and Dec grants only. Test: Task 1.
3. **Concurrent requests**: two simultaneous requests that would each fit the balance but together go negative (no negative allowed) leave at most one PENDING; both take the person's advisory lock (`timerLock`). Test: Task 5.
4. **A person whose timezone differs from the workspace's**: an entry at 23:30 Sunday in Manila for a New York workspace lands on the person's Sunday in Attendance; the weekly subtotal uses the workspace week start. Test: Task 6.
5. **Import twice, or rename then import**: importing PH 2027 twice adds nothing the second time; after an admin renames an imported row, a new import offers the dataset's name on that date unticked, labelled "Already imported as <new name>", so the renamed day is not doubled by accident. Test: Task 2 (`planHolidayImport`) and Task 4 (`importHolidays`).
