# Data model

PostgreSQL (16 locally, Supabase in production) via Drizzle ORM. Schema source: `packages/db/src/schema/*.ts`; migrations in `packages/db/migrations/`. All timestamps are `timestamptz` in UTC. IDs are text (Better Auth generates its own; our code uses UUIDs).

## Entity overview (Phases 0–4a)

```
user ──< session            (activeWorkspaceId → workspace)
user ──< account            (credential password hash, OAuth tokens)
verification                (email verification, password reset, magic link tokens)

workspace ──1 workspace_settings
workspace ──< membership >── user
workspace ──< invitation    (inviterId → user)

workspace ──< client
workspace ──< project >── client   (nullable, ON DELETE RESTRICT)
project ──< project_member >── user   (who may see a PRIVATE project)
project ──< project_favorite >── user
project ──< task ──< task_assignee >── user
workspace ──< tag
workspace ──< time_entry >── user
time_entry >── project      (nullable, ON DELETE SET NULL)
time_entry >── task         (nullable, ON DELETE SET NULL)
time_entry ──< time_entry_tag >── tag
user ──1 user_settings      (tracker preferences, created lazily)
user ──< timesheet_template (per workspace)
workspace ──< report_share_link >── user   (creator; public read-only report links)
workspace ──< user_group ──< user_group_member >── user;  project ──< project_group >── user_group
workspace ──< managed_user / managed_group   (a manager's people and groups)
workspace ──< rate   (billable rate history per level);  workspace ──< rate_recalc_job
workspace ──< export_job >── user          (large exports built after the response)
```

### time_entry

| Column | Type | Notes |
| --- | --- | --- |
| id | text PK | UUID |
| workspace_id | text → workspace (cascade) | |
| user_id | text → user (cascade) | |
| description | text | default `''`, max 3000 (validated in `packages/core`) |
| project_id | text? → project (set null) | indexed |
| task_id | text? → task (set null) | indexed; must belong to `project_id` |
| billable | boolean | default false |
| start | timestamptz | |
| end | timestamptz? | `NULL` = running. Reserved word: always quote `"end"` in raw SQL |
| duration_seconds | integer? | set on stop and on every edit; `NULL` while running |
| billable_rate_minor | bigint? | the hourly rate the entry was saved with, in minor units (Phase 4) |
| rate_currency | char(3)? | ISO 4217 code of that rate |
| rate_source | `rate_level`? | which level answered: `task`, `project_member`, `project`, `member`, `workspace` |
| amount_minor | bigint? | `round(rate × duration_seconds / 3600)` half up; `NULL` while running or without a rate |
| deleted_at | timestamptz? | soft delete (Undo restores it) |
| created_at, updated_at | timestamptz | |

Indexes:

- `time_entry_workspace_user_start_idx` on `(workspace_id, user_id, start DESC)`: the tracker list and its week pagination.
- `time_entry_project_id_idx` on `project_id`; `time_entry_task_id_idx` on `task_id`.
- `time_entry_workspace_start_idx` on `(workspace_id, start) WHERE deleted_at IS NULL AND "end" IS NOT NULL`: team-wide report scans (Phase 3); a member's own report uses the user index above.
- `time_entry_one_running_uq`: `UNIQUE (workspace_id, user_id) WHERE "end" IS NULL AND "deleted_at" IS NULL`. This enforces invariant 4. Soft-deleted rows are excluded so they can never block a new timer.

Rules (enforced in `apps/web/src/server/time-entries.ts`, the only write path):

- Starting a timer takes `pg_advisory_xact_lock(hashtext(workspace_id || ':' || user_id))`, stops the running entry and inserts the new one in one transaction. The unique index is the backstop and surfaces as a `CONFLICT` error.
- Stops and edits lock the row with `SELECT ... FOR UPDATE`; an edit writes `start`/`end`/`duration_seconds` only when the patch changes a time.
- `end > start`; at most 999 hours; a timer cannot stop more than one minute in the future. A forgotten timer that passes 999 hours is clamped at 999 hours when stopped.
- An entry that crosses midnight stays one row and is listed under its start date in the viewer's timezone.
- Rates (Phase 4, decision 3 of the Phase 4 design): a new entry is rated with the rate in force at its start; an edit keeps the rate and recomputes `amount_minor`; only a change of project, task, person or billable switched on re-rates it. A rate change re-rates saved entries only through the `rate_recalc_job` ("Entries from a date" / "All entries"). The rating SQL lives in `packages/db/src/rates-sql.ts`, shared by the entry service, the job and the seed.

### user_group, user_group_member, project_group

`user_group` (`id`, `workspace_id` cascade, `name` unique per workspace, timestamps); `user_group_member` (`group_id` cascade, `user_id` cascade, PK both, index on `user_id`); `project_group` (`project_id` cascade, `group_id` cascade, PK both): a group's members see and track on that PRIVATE project.

### managed_user, managed_group (manager scope)

A manager's scope is own time, the people in `managed_user` (`workspace_id`, `manager_id`, `user_id`) and the current members of the groups in `managed_group` (`workspace_id`, `manager_id`, `group_id`), plus every entry on a project where they are `project_member.is_manager`. Rows exist only for people with the `manager` role; changing their role away from manager deletes them.

### invitation_group

`(invitation_id → invitation cascade, group_id → user_group cascade)`: the groups an invitee joins when they accept (Better Auth owns `invitation`).

### rate_recalc_job

"Apply to past entries": `id`, `workspace_id`, `created_by`, `from`, `status` (`queued` | `running` | `done` | `failed`), `total`, `processed`, `cursor_start` + `cursor_id` (the last entry done, so Retry resumes there), `error`, `created_at`, `started_at`, `finished_at`. Index on `(workspace_id, created_at DESC)`. Run after the response in keyset batches; one job runs per workspace, and a second request lowers the queued job's `from` instead of adding another.

## Row-level security

Every table enables RLS (`.enableRLS()` on each `pgTable`, migration `0003`) with no policies, and migration `0004` revokes all privileges on `public` from Supabase's `anon` and `authenticated` roles. Supabase's Data API therefore reads nothing; the app connects as the table owner (`timekeep_app` in production) and is unaffected. New tables must call `.enableRLS()`; `apps/web/src/server/rls.test.ts` fails otherwise.

## Report performance (Phase 3)

`pnpm db:seed:perf` builds a local `perf` workspace (25 people, 1,000,000 stopped entries over three years); `pnpm --filter @timekeep/web report:perf` times the one-year Summary grouped by client and project (334k entries) and fails over one second. Recorded 2026-10-25 on the local Postgres 16 container (default `shared_buffers` 128 MB, smaller than the 255 MB table) with the machine's CPU otherwise busy:

| Run | Median |
| --- | --- |
| Three sequential queries, `to_char` week key per row | 1258 ms |
| Two concurrent queries, totals summed from the series, series by local day rolled up in code | 757 ms |

What the plans show:

- Both remaining queries scan the table sequentially: a year is a third of the workspace, so the partial `time_entry_workspace_start_idx` loses to a scan here. It earns its keep on narrower ranges.
- The grouped query runs as a parallel hash aggregate (2 workers, about 330 ms). The planner removes the unused `project`, `client` and `task` left joins.
- The series query stays on one worker (about 600 ms): Postgres estimates one group per row for any expression on `start`, so it never chooses a partial aggregate. Grouping by `(start at time zone tz)::date` (one conversion per row) and rolling days into weeks or months with `bucketKeyOfDay` keeps it cheap. A per-row `to_char` or week expression cost twice as much.
- Not needed yet: a `work_mem` bump (aggregates use under 4 MB) or the day-level rollup table the spec keeps as the last resort.

## Rates and scope at scale (Phase 4a)

Measured on the perf tenant (`pnpm db:seed:perf`: 1,000,000 entries, rates at four levels, a manager of 6 people and 1 project), with `pnpm --filter @timekeep/web report:perf`, 2026-10-27:

- "Apply to past entries" over every entry (`runRateRecalcJob`, batches of 5,000, one `rateEntriesSql` update each): 76.2 s for 1,000,000 entries, inside a function's 300 s. One batch is about 380 ms (a primary-key scan plus five rate-lookup probes per entry).
- One-year Summary with amounts: owner median 328 ms (334,000 entries), manager median 146 ms (109,000 entries in scope). The amount is one more `sum(bigint)` over a stored column; the scope filter is an `OR` of the manager's own, managed people's and managed projects' entries.
