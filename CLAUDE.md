# TimeKeep — guide for engineers and AI agents

TimeKeep is a web-based time tracking and timesheet SaaS for teams (functionally comparable to Clockify; **never** copy its brand, text or assets). It is built in ten phases, one Claude Code session per phase, following `docs/PRD.md` and `docs/PROGRESS.md`.

## Commands

| Command | Purpose |
| --- | --- |
| `pnpm install` | Install everything (pnpm 10, Node 22+) |
| `cp .env.example .env` | One root `.env`; every app/package loads it via `dotenv -e ../../.env` |
| `docker compose up -d --wait` | Postgres 16 (`:5432`), Mailpit (`:8025` UI, `:1025` SMTP), RustFS S3 (`:9000` API, `:9001` console) |
| `pnpm storage:init` | Create the bucket + public-read policy for `avatars/*`, `logos/*`, and the private `S3_EXPORT_BUCKET` for export files (any S3-compatible backend) |
| `pnpm db:migrate` / `pnpm db:generate` / `pnpm db:seed` / `pnpm db:studio` | Drizzle migrations, generate from schema, demo data, studio |
| `pnpm bootstrap` | compose up + storage:init + migrate + seed (not `setup`: that is a pnpm built-in and silently shadows package scripts) |
| `pnpm dev` | Web (`http://localhost:3000`) and worker, via Turborepo |
| `pnpm lint && pnpm typecheck && pnpm test && pnpm e2e` | The full gate. Run it before saying a phase is done |
| `pnpm --filter @timekeep/web e2e -- --ui` | Playwright UI mode |
| `pnpm --filter @timekeep/web build && CI=1 AUTH_RATE_LIMIT_ENABLED=false pnpm --filter @timekeep/web e2e` | The suite against a production server, as CI and previews run it (the dev server can drop a popover under three workers; the production rate limit must be off) |
| `pnpm --filter @timekeep/web e2e:coverage` | Check `docs/E2E_COVERAGE.md`: every ticked line must name a listed, non-skipped test (runs in CI) |
| `E2E_BASE_URL=<preview url> pnpm --filter @timekeep/web e2e` | Run the e2e suite against a Vercel preview (also needs `E2E_SECRET`, `VERCEL_AUTOMATION_BYPASS_SECRET`) |
| `pnpm db:e2e-cleanup` | Delete throwaway `@e2e.test` users, e2e-only workspaces and old captured email |
| `pnpm db:seed:perf` then `pnpm --filter @timekeep/web report:perf` | Local only: a `perf` workspace with 1,000,000 entries, then time the one-year Summary (fails over 1 s) and print its plans |

Demo login after seeding: `owner@demo.test` / `password123` (also `admin@`, `manager@`, `member1@`, `member2@` — same password). Demo workspace slug: `demo`.

## Invariants (do not break these)

1. **Timestamps are UTC.** Every column is `timestamptz`; render in the viewer's timezone (`user.timezone` → `workspace_settings.timezone` → UTC).
2. **Money is integer minor units + ISO 4217 currency code.** Never floats. (From Phase 4.)
3. **Every query is scoped by `workspaceId` and checked against the permission matrix.** Server actions and route handlers call `requireWorkspaceAccess(slug)` (membership) from `apps/web/src/server/workspace-access.ts`, then `authorize(ctx, action, resource)` (or `authorizeProject`) from `server/authz.ts`; pages/layouts use `requireWorkspacePage` and `authorizePage` (`server/authz-page.ts`). Cross-tenant access must render not-found, never leak existence: non-members get the same 404 as an unknown slug; a resource outside the actor's scope (another person's entry, a private project, a member outside a manager's team) is a 404 too; 403 is only for a role or setting that never allows the action.
4. **At most one running timer per user per workspace**, enforced by the partial unique index `time_entry_one_running_uq` (`WHERE "end" IS NULL AND deleted_at IS NULL`) plus a per-user advisory lock in `startTimer`. Starting a timer stops the running one in the same transaction.
5. **Rates are snapshotted on the entry** so historical reports never shift: a rate change re-rates saved entries only through the "apply to past entries" job.
6. **No feature merges without tests.** Pure logic → Vitest in `packages/core`; DB behaviour → Vitest integration tests in `apps/web/src/**/*.test.ts` against `TEST_DATABASE_URL`; user flows → Playwright in `apps/web/e2e`. From Phase 2, a feature starts with unticked lines in `docs/E2E_COVERAGE.md` and failing e2e tests before any app code.
7. **Secrets never enter git.** The repo is public. `.env` is ignored; `.env.example` documents every variable.

## Conventions

- TypeScript strict, `noUncheckedIndexedAccess` on. Prefer `import type` / inline `type` imports (lint enforces it).
- Server code imports `server-only`. Server actions live in `src/server/actions/*.ts` with `"use server"` at the top and return `ActionResult<T>` (`src/lib/action-result.ts`) instead of throwing to the client. JSON route handlers end in `routeErrorResponse(error, scope)` (`workspace-access.ts`): access errors keep their status, `BadRequestError` is a 400, anything else is logged and answered 500.
- **Permissions** (`packages/core/src/permissions.ts`): one typed matrix answers who may do what: `can(actor, action, resource)`, and `denial()` (403 for a role or setting, 404 when the resource is outside the scope). Actions are a fixed vocabulary; nobody changes, deactivates or removes the owner, or deactivates or removes themselves. `docs/PERMISSIONS.md` is generated (`pnpm permissions:doc`; a test fails while it is stale). `authorize-coverage.test.ts` fails when an exported action or a `/api/w` route resolves a workspace without calling `authorize` (or a listed helper). The `Actor` (`server/authz.ts` `loadActor`, cached per request by `viewerFor(ctx)`) carries a manager's scope: the people in `managed_user`, the current members of their `managed_group`s, and the projects where `project_member.is_manager`. Every `Viewer` (and `EntryScope`) carries its actor. `authz.ts` and `access-error.ts` import nothing from Next, so scripts (`report:perf`) can load them.
- **Team** (`server/team.ts`, `groups.ts`, `invites.ts`): role, status, removal, ownership and manager scope write `membership` directly after the matrix allows them (Better Auth keeps invitations only). Deactivating stops a running timer and closes the workspace (the same 404); removing deletes groups, project memberships and scope but keeps entries ("(former member)") and rates (so re-rating keeps their amounts). Leaving the manager role clears the scope. Bulk invite and the CSV user import send one Better Auth invitation (and email) per address; `invitation_group` joins the invitee to groups on acceptance (`afterAcceptInvitation`). A group on a private project (`project_group`) lets its members see and track on it. `setProjectMembers` keeps a project's managers.
- Validation: zod schemas live in `packages/core/src/schemas.ts` and are shared by forms (react-hook-form + `zodResolver`) and server actions. Validate on both sides.
- Database access goes through Drizzle (`@timekeep/db`). `getDb()` is a lazy singleton; tests create their own client with `createDb(TEST_DATABASE_URL)`.
- Auth is Better Auth. Its organization plugin is renamed: `organization → workspace`, `member → membership` (+ `status`), `invitation`, `session.activeOrganizationId → activeWorkspaceId`. Roles are stored lowercase (`owner | admin | manager | member`); `packages/core/src/roles.ts` is the single source of truth for ranking.
- Workspaces are created only through `createWorkspace()` in `apps/web/src/server/workspaces.ts` (row + settings + owner membership in one transaction). Pending invites live in `invitation`; a `membership` row appears on acceptance.
- Email goes through `sendEmail()` in `apps/web/src/server/mail.ts` (SMTP; Mailpit locally). Phase 5 moves sending into the worker.
- Files go to S3-compatible storage via `apps/web/src/server/storage.ts` (RustFS locally — MinIO stopped publishing community images; the API is identical). `apps/web/scripts/storage-init.ts` creates the bucket and makes `avatars/*` and `logos/*` public-read. Validate MIME + magic bytes + size before uploading.
- **Time entries are written only through `apps/web/src/server/time-entries.ts`** (db-injected functions, scoped to one workspace + user). Server actions in `actions/time-entries.ts` wrap it; `createManualEntries` is its one batch path (the CSV import). Later phases add locks and approvals there, so never insert or update `time_entry` anywhere else; the one other writer is the rating SQL in `packages/db/src/rates-sql.ts` (the recalculation job and the seed).
- **Rates** (`server/rates.ts`, core `rates.ts` and `money.ts`): five levels, most specific first: task, project member, project, member, workspace. Rows are never edited; a change adds a row with `effective_from` (a second change on the same date replaces it), and a null amount means "no rate at this level from this date". An entry is rated when created, with the rate in force at its start; an edit keeps the rate and recomputes the amount; only a change of person, project or task, or billable switched on, re-rates (`needsRerate`). The rate dialog's "New entries only" is effective from today's midnight in the workspace timezone; "Entries from a date" and "All entries" queue the `rate_recalc_job` (`rate-recalc.ts`), run after the response in keyset batches that commit progress and the cursor (Retry resumes; one job per workspace; a new request folds in the waiting job and any failed one: the earliest date, started over; polling `/api/w/[slug]/rate-recalc` fails a job killed mid-run and starts a waiting one nobody runs). `rateEntriesSql` is the only resolution in SQL, tested to agree with core's `resolveRate`. Money: `parseMoney` reads typed amounts as digits (never `parseFloat`), `amountFor` is BigInt half-up, `formatMoney` passes Intl a decimal string. One currency per workspace until Phase 6: changing it relabels rates and snapshots after a confirmation. Owners and admins set rates; owners, admins and managers (in their scope) see amounts; members never.
- **Workspace rules** (Phase 4b; `packages/core/src/workspace-rules.ts`, read by `loadActor` from `workspace_settings` in one query per request): report rounding, hidden pages, who can create, who sees the team's time, required fields, force timer and breaks; every column defaults to the behaviour before the rule existed. A hidden page is a 404 page and a 403 JSON route. Required fields and force timer are enforced in the entry service: `assertRequiredFields` on stop, save, edit, bulk edit and import (a task only when the project has active tasks; breaks exempt); `assertCanWriteTimes` is the matrix's `entry.writeTimes` (manual times refused under force timer for the actor's own entries only; a stop with an explicit end stays allowed). A break (`time_entry.type = 'break'`, `breakAware`) has no details, needs `allow_breaks`, is never rated (`rates-sql.ts` rates work only) and keeps its type; reports count work unless the `type` filter says otherwise; the timesheet grid lists work only.
- **Rounding is a report rule**, never stored on entries: the engine reads it with the currency (`reportSettings`, `ruleFor(query, settings)`), `measures(rule)` sums `roundedSecondsSql` / `roundedAmountSql` (`packages/db/src/rounding-sql.ts`, tested to agree with core `roundDuration`), the URL `rounding=off` shows raw time, the Detailed report sorts by raw duration, and the dashboard asks for raw.
- **Add time for others**: `EntryScope = Viewer & { actedBy?: Actor }`. `scopeForUser(db, viewer, userId)` / `targetScope(ctx, userId)` give the target's own viewer plus the actor after `entry.write`; `scopesForEntries(db, viewer, ids)` resolves the owners of existing entries, so writes take entry ids and creates take a `userId`; a member asking for anyone else is a 404; `writableUsers` lists who the person picker offers. Entry routes take `?userId=`, query keys carry the person (`trackerKeys.entries(slug, userId)`), the tracker, timesheet and calendar read it from `TargetProvider` / `useTarget`, and the timer bar is always the viewer's own.
- **Power features**: bulk edit is all-or-nothing (`bulkUpdateEntries` over the owner groups from `scopesForEntries`); `splitEntry` keeps the rate on both parts; favourites (`favorite_entry`, `server/favorites.ts`) pin details, never times, 20 per person; templates are projects with `is_template` (`listTemplates`, `copyProject` copies tasks, members, groups and rates), hidden from the projects list and the pickers; the Audit tab is the Detailed report with `audit`, `shortMinutes` and `longHours` in the query (`auditConditions`, OR); the CSV import is `POST /api/w/[slug]/time-entries/import` (multipart; `?dryRun=1` plans, the plan's `fingerprint` guards the commit; `server/entry-import.ts`) and writes through `createManualEntries`.
- **Date, time and duration maths only via `packages/core`**: `parseDuration` / `formatDuration` / `formatClock`, `localDateKey`, `zonedDateTimeToInstant`, `addDaysInZone`, `weekBounds`, `formatTimeOfDay`, `parseTimeOfDay`, and `entry-edit.ts` for row edits. They are DST-safe (built on `@date-fns/tz`); never add `n * 86_400_000` to an instant. Viewer preferences come from `resolveViewerPrefs(user, workspaceSettings)`.
- Bare numbers typed as durations are hours (`1.5` = 1:30:00); `1:30`, `90m`, `1h30m` also work.
- **Catalog** (clients, projects, tasks, tags): services in `src/server/catalog/*` take a `Viewer` (`workspaceId`, `userId`, `role`, `actor`) and apply the matrix's `project.view` (admins see everything; others see public projects and private ones they are on, directly or through a group). A private project a member is not on is "not found", never "forbidden". `trackingBlock` says why details cannot take new time (archived project, done task, archived tag); the entry service applies it on start, manual create, continue, duplicate and detail changes. Owners and admins manage the catalog; a project's managers edit their project (not its deletion: `project.delete` is admin-only); the "who can create" setting (Phase 4b) can open creation to managers or everyone. Patch schemas are explicit (`projectPatchSchema`, `clientPatchSchema`, …): zod 4 `.partial()` keeps field defaults, which would reset untouched columns.
- **Tasks by group** (decision 11 of the Phase 4 design, 2026-10-29): `workspace_settings.task_visibility` (`EVERYONE`, the default, or `BY_GROUP`) and the `task_group` table (`task_id`, `group_id`; departments are the existing user groups). `visibleTasksFor(db, viewer, { projectIds?, includeHidden? })` in `server/catalog/tasks.ts` is the one source of member-facing task lists: every active task until the workspace shows tasks by group, then owners and admins all, a manager the tasks of projects they manage plus their groups', a member their groups' only, and a task with no group nobody's. `task-visibility-coverage.test.ts` lists every server module that may read task rows; a new reader fails it. `listPickerProjects` builds its tasks from it and drops a project whose active tasks the person cannot see at all (rule 8). `task.trackTime` is checked in `assertDetailsUsable` wherever a task is assigned, against the entry owner's actor (rule 11: add-for-others, bulk edit and import follow), with `TASK_UNAVAILABLE_MESSAGE`; an entry keeps a task it already has (rule 10), and a split copies it. `assertTaskPicked` is rule 8: on Stop and on saves that touch the project or task, a manager or member on a project with active tasks must pick one (`Task is required.`), never on Start or a time edit. `task.create` and `task.assignGroups` are owner, admin and the project's managers; `setTaskGroups` and `createTask` give a private project's access to the groups in the same transaction (rule 9). With tasks by group a task is never created without a group (the task dialog, the import's "Groups for new tasks"); the picker's inline "Create task" shows only in everyone mode. `Actor.groupIds` is loaded only in `BY_GROUP` mode. `task_assignee` and `task_creators` stay in the schema, unread.
- Pickers: `ProjectPicker` takes and returns `{ projectId, taskId }` (a task implies its project) and shows the entry's own project/task (`current`) when the options no longer list it; the same for `TagPicker` and archived tags.
- Timesheet and calendar read the viewer's entries for a range through `/api/w/[slug]/time-entries/range` under the `trackerKeys.range` key, which sits under the tracker's `entries` prefix, so any entry write (`useEntryWrites`, the list's mutations, another tab) refetches every view. Their maths is pure in `packages/core/src/timesheet.ts` and `calendar.ts`.
- **Reports** (`src/server/reports.ts`): one engine for Summary, Detailed, Weekly, the dashboard, the project Status tab, exports and share links, so their numbers cannot drift. It counts stopped, live entries only, scoped by workspace and by `scopeFilter(actor)` (owners and admins everyone, a manager their scope, a member their own); `effectiveQuery` also pins a member's `userIds` whatever the URL says, and a manager's Users or Groups filter narrows within the scope, never widens it. Amounts (`amountMinor`, `unratedCount`) and `money: { currency }` reach only viewers with `report.viewAmounts`; for everyone else money is null and every amount is zeroed on the server. A share link shows amounts only when made with "Include amounts" and while its creator may still see them. Grouping keys, presets, buckets and sort columns are fixed vocabularies in `packages/core/src/reports.ts`, never strings from the URL. The report query is the URL (`parseReportQuery` / `reportQueryToSearchParams`); filter changes go through the History API, not the router, so no server render runs: `pushState`, so Back undoes a filter, except typed text, which uses `replaceState`. A popover has no exit animation, because Radix keeps a closing popover as the top layer and it would swallow the next Escape. Report data sits under `trackerKeys.report`, inside the tracker's `entries` prefix, so any entry write refetches it. SQL groups by ordinal (`sql.raw("1")`): Drizzle numbers the same parameter differently in SELECT and GROUP BY. Duration sums are `::bigint` with `.mapWith(Number)` (`int` overflows at 2^31 s). The Detailed report pages by keyset on `(sort column, id)` and sums the range on the first page only. Grouping by `tag` repeats a multi-tag entry, so the levels above a tag level take their totals from a second query without the tag join (`groupRows(rows, keys, totals, prefixRows)`). A custom range is a year at most. The Weekly rows choice is the query's `weeklyBy`, so exports and share links follow it. Links into the Detailed report go through core `drillDownQuery` (`lib/report-links.ts`).
- **Exports** read one column record per report (`packages/core/src/report-export.ts`) for CSV (BOM, CRLF) and Excel; the PDF prints a self-contained HTML template in headless Chromium (`report-pdf.ts`). Over `EXPORT_JOB_THRESHOLD` rows (default 10,000) or 4 MB, an export becomes an `export_job` run with `after()` (`runExportJob`, a single call so it can move to pg-boss), stored in the private `S3_EXPORT_BUCKET`, downloaded through a 15-minute presigned URL, and the owner is emailed. Export files never go in the public bucket. CSV text cells that start a formula (`=`, `+`, `-`, `@`, tab, CR) get a leading apostrophe.
- PDF routes need Chromium's binary traced in: `next.config.ts` `outputFileTracingIncludes` keys are globs (`*` for dynamic segments) and the include is the package's real path (pnpm links). A new route that prints a PDF must be added there.
- **Share links** store only the sha256 of a 32-byte token, plus the effective query and the creator's preferences; they read with the creator's current role. Revoked, expired, unknown, or a creator who left: the same 404. The public export allows one download per link every 10 s (`claimShareExport`, 429 otherwise).
- `components/calendar/event-sources.ts` is the extension point for Google/Outlook events; nothing syncs yet.
- Tracker data flow: the page SSRs the first week into react-query (`HydrationBoundary`); later pages and refetches use the `/api/w/[slug]/...` route handlers; writes are server actions followed by cache updates (`components/tracker/entry-cache.ts`). Everything crossing the boundary is JSON with ISO strings (`lib/tracker-types.ts`), never `Date`.
- `TrackerProvider` (in the workspace layout) owns the running timer on every workspace page: tab title, S / N / Esc shortcuts, cross-tab sync (BroadcastChannel + refetch on focus), idle detection, Pomodoro and reminders. Components that need the ticking clock use `useTrackerClock()`; everything else uses `useTracker()` so rows do not re-render every second.
- `react-hooks` v7 lint rules are on: no `Date.now()` or other impure calls during render, no synchronous `setState` in effects (use `useSyncExternalStore`, `useEffectEvent`, or derive state), and `useWatch` instead of `form.watch`.
- **e2e suite** (design: `docs/superpowers/specs/2026-10-18-e2e-suite-design.md`):
  - Import `test` and `expect` from `e2e/fixtures.ts`. Fixtures:
    - `freshUser`: a new `@e2e.test` account, signed in over HTTP, in a time zone where it is about noon (so no test crosses local midnight). Fixtures are lazy, so request it explicitly. `signUpFreshUser(request, baseURL)` makes another one in a separate context.
    - `demoUser(role)`: only for role and isolation tests.
    - `trackerPage()`: opens the tracker once it is interactive.
  - Each test creates its own data (`e2e/helpers/tracker.ts` `addManualEntry` at explicit early times) and must pass in any order.
  - Wait for `data-hydrated="true"` (timer bar, or the shell's `<main>`) before typing or pressing keys.
  - Wait for `[data-saving="false"]` before reloading after an edit.
  - `docs/E2E_COVERAGE.md` lists every user-facing function. `pnpm --filter @timekeep/web e2e:coverage` (run in CI) fails when a ticked line names a missing test.
  - Tick a line only after its test was seen to fail with the guarded behaviour broken; the commit message records the break.
  - `test.skip` / `test.fixme` in `e2e/` are lint errors (a skip inside a test body is invisible to the coverage check). A deliberate skip needs an `eslint-disable` with a reason, and its coverage line is unticked.
  - The suite must stay under 10 minutes on a Vercel preview; slow tests move to a nightly run rather than being deleted.
  - Local runs clean up `@e2e.test` users in a global teardown that only ever touches a local database.
  - Helpers under `e2e/helpers/` can have Vitest unit tests named `*.unit.test.ts`; Playwright ignores them.
- UI: shadcn/ui components from `@timekeep/ui/components/*`, icons from `lucide-react`, toasts via `sonner`. Theme tokens are in `packages/ui/src/styles/globals.css` (our own teal palette; light + dark via `.dark` class and `next-themes`). Every page must work at 375px.
- Next.js: `cacheComponents` is **off** (all pages are dynamic and auth-gated). `PageProps<"/route">` / `LayoutProps<"/route">` global types come from `next typegen` (run by `pnpm typecheck`).
- Commit after each numbered part of a phase prompt; message body explains what and why. Tag `phase-N` when a phase's acceptance checks pass.

## Deployment (Vercel + Supabase)

- Vercel project `time-keep` (root `apps/web`, region `sin1`), linked to GitHub: every push gets a preview, `main` deploys production. Deployment protection is on; automation uses the bypass secret.
- **One Supabase project holds production and every preview** (tenant = workspace). So:
  - **Previews never migrate.** `scripts/vercel-build.ts` runs `db:migrate` only when `VERCEL_ENV=production`. A schema-changing branch first applies its migrations to the shared database with the **Migrate shared database** workflow (Actions → `migrate.yml` → run on the branch, type `migrate`): the expand step, so the preview can seed and run e2e before the merge, and the production build then has nothing to apply. Until then `pnpm db:seed` refuses to run (pending migrations) rather than half-seed the demo tenant. Test schema changes locally before that.
  - **e2e stays in its own tenants**: `@demo.test` demo users and the `demo` workspace, throwaway `@e2e.test` users. Seeding and `db:e2e-cleanup` only touch workspaces whose members are all such users; never widen that.
  - **`pnpm test` must never point at Supabase**: it truncates every table.
- The app connects through Supavisor in **transaction mode** (port 6543): no named prepared statements, `SET`, `LISTEN/NOTIFY` or session-level advisory locks (transaction-scoped `pg_advisory_xact_lock` is fine). Migrations, seed and cleanup use `DATABASE_URL_SESSION` (port 5432).
- **Every table enables RLS** (`.enableRLS()` on each `pgTable`) and the `anon`/`authenticated` roles have no privileges on `public`, so Supabase's Data API can read nothing. `rls.test.ts` fails if a new table misses it.
- Production and previews set `S3_EXPORT_BUCKET=timekeep-exports` (a private Supabase bucket); previews also set `EXPORT_JOB_THRESHOLD=5`, the value the e2e job test uses (Playwright's local web server sets the same).
- Previews set `MAIL_CAPTURE=true`: email is stored in `captured_email` instead of sent, and the e2e suite reads it from `/api/test/emails` (404 without `E2E_SECRET`, and always in production).
- `.github/workflows/e2e-preview.yml` runs on every successful preview deployment: seed, e2e against the deployment URL, then cleanup.
- **Shared-database safety rules.**
  - Seed and cleanup never delete a demo or e2e user who belongs to a customer workspace: reseeding fails loudly, and cleanup skips that user.
  - Previews capture mail only for `@e2e.test` / `@demo.test` recipients and drop everything else, because preview tokens are valid in production.
  - `test/safe-test-db.ts` refuses any non-local `TEST_DATABASE_URL`.
  - Remote Playwright runs record no traces, because they would capture the bypass header and artifacts are public.
- **Never authorize a Vercel deployment of a fork PR.** Git fork protection is on. An authorized fork build would run with the preview environment, which holds production database credentials, and the e2e workflow would run the fork's code with repository secrets.
- **Migrations must be backward-compatible (expand, then contract).** While a production build runs, live production and every open preview still run old code against the new schema.
- **An index on a large table is built concurrently, by hand, first.** Drizzle runs each migration in a transaction, where `CREATE INDEX CONCURRENTLY` is impossible, and a plain `CREATE INDEX` locks the table against writes while it builds. Before the migration is applied anywhere, change its statement to `CREATE INDEX IF NOT EXISTS` (editing an unapplied migration is fine). Then run `CREATE INDEX CONCURRENTLY IF NOT EXISTS …` with the same name and definition over `DATABASE_URL_SESSION`, and check that it is valid (`pg_index.indisvalid`). The migration then finds the index and does nothing. `time_entry_workspace_start_idx` (0007) was built the plain way while the table was small.

## Working on a phase

1. Read `docs/PRD.md`, `docs/DATA_MODEL.md` and the phase checklist in `docs/PROGRESS.md`.
2. Plan first (folder tree, schema changes, file list), then build part by part.
3. Add a migration with `pnpm db:generate` for every schema change; never edit applied migrations.
4. Finish with `pnpm lint && pnpm typecheck && pnpm test && pnpm e2e`, update `docs/DATA_MODEL.md` and `docs/PROGRESS.md`, update this file if conventions changed, commit, tag.
5. Keep `docs/BACKLOG.md` current: add every deferred finding (review minors, gaps a test run exposed, setup left for later), and move an item to its Done section, with date and commit, in the same commit that fixes it.
