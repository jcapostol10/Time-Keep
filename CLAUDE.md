# TimeKeep — guide for engineers and AI agents

TimeKeep is a web-based time tracking and timesheet SaaS for teams (functionally comparable to Clockify; **never** copy its brand, text or assets). It is built in ten phases, one Claude Code session per phase, following `docs/PRD.md` and `docs/PROGRESS.md`.

## Invariants (do not break these)

1. **Timestamps are UTC.** Every column is `timestamptz`; render in the viewer's timezone (`user.timezone` → `workspace_settings.timezone` → UTC).
2. **Money is integer minor units + ISO 4217 currency code.** Never floats. (From Phase 4.)
3. **Every query is scoped by `workspaceId` and checked against the permission matrix.** Server actions and route handlers call `requireWorkspaceAccess(slug)` (membership) from `apps/web/src/server/workspace-access.ts`, then `authorize(ctx, action, resource)` (or `authorizeProject`) from `server/authz.ts`; pages/layouts use `requireWorkspacePage` and `authorizePage` (`server/authz-page.ts`). Cross-tenant access must render not-found, never leak existence: non-members get the same 404 as an unknown slug; a resource outside the actor's scope (another person's entry, a private project, a member outside a manager's team) is a 404 too; 403 is only for a role or setting that never allows the action.
4. **At most one running timer per user per workspace**, enforced by the partial unique index `time_entry_one_running_uq` (`WHERE "end" IS NULL AND deleted_at IS NULL`) plus a per-user advisory lock in `startTimer`. Starting a timer stops the running one in the same transaction.
5. **Rates are snapshotted on the entry** so historical reports never shift: a rate change re-rates saved entries only through the "apply to past entries" job.
6. **No feature merges without tests.** Pure logic → Vitest in `packages/core`; DB behaviour → Vitest integration tests in `apps/web/src/**/*.test.ts` against `TEST_DATABASE_URL`; user flows → Playwright in `apps/web/e2e`. From Phase 2, a feature starts with unticked lines in `docs/E2E_COVERAGE.md` and failing e2e tests before any app code.
7. **Secrets never enter git.** The repo is public. `.env` is ignored; `.env.example` documents every variable.

## Conventions

- TypeScript strict, `noUncheckedIndexedAccess` on. Prefer `import type` / inline `type` imports (lint enforces it).
- Server code imports `server-only`. Server actions live in `src/server/actions/*.ts` with `"use server"` at the top and return `ActionResult<T>` (`src/lib/action-result.ts`) instead of throwing to the client. JSON route handlers end in `routeErrorResponse(error, scope)` (`workspace-access.ts`): access errors keep their status, `BadRequestError` is a 400, anything else is logged and answered 500.
- **Permissions** (`packages/core/src/permissions.ts`): one typed matrix answers who may do what: `can(actor, action, resource)`, and `denial()` (403 for a role or setting, 404 when the resource is outside the scope). Actions are a fixed vocabulary; nobody changes, deactivates or removes the owner, or deactivates or removes themselves. `docs/PERMISSIONS.md` is generated (`pnpm permissions:doc`; a test fails while it is stale). `authorize-coverage.test.ts` fails when an exported action or a `/api/w` route resolves a workspace without calling `authorize` (or a listed helper). The `Actor` (`server/authz.ts` `loadActor`, cached per request by `viewerFor(ctx)`) carries a manager's scope: the people in `managed_user`, the current members of their `managed_group`s, and the projects where `project_member.is_manager`. Every `Viewer` (and `EntryScope`) carries its actor. `authz.ts` and `access-error.ts` import nothing from Next, so scripts (`report:perf`) can load them.
- **Team** (`server/team.ts`, `groups.ts`, `invites.ts`): role, status, removal, ownership and manager scope write `membership` directly after the matrix allows them (Better Auth keeps invitations only). Deactivating stops a running timer and closes the workspace (the same 404); removing deletes groups, project memberships and scope but keeps entries ("(former member)") and rates (so re-rating keeps their amounts). Leaving the manager role clears the scope. Bulk invite and the CSV user import send one Better Auth invitation (and email) per address; `invitation_group` joins the invitee to groups on acceptance (`afterAcceptInvitation`). A group on a private project (`project_group`) lets its members see and track on it. `setProjectMembers` keeps a project's managers.
- Validation: zod schemas live in `packages/core/src/schemas.ts` and are shared by forms (react-hook-form + `zodResolver`) and server actions. Validate on both sides.
- Database access goes through Drizzle (`@timekeep/db`). `getDb()` is a lazy singleton; tests create their own client with `createDb(TEST_DATABASE_URL)`.
- Auth is Better Auth. Its organization plugin is renamed: `organization → workspace`, `member → membership` (+ `status`), `invitation`, `session.activeOrganizationId → activeWorkspaceId`. Roles are stored lowercase (`owner | admin | manager | member`); `packages/core/src/roles.ts` is the single source of truth for ranking.
- Workspaces are created only through `createWorkspace()` in `apps/web/src/server/workspaces.ts` (row + settings + owner membership in one transaction). Pending invites live in `invitation`; a `membership` row appears on acceptance.
- Email goes through `sendEmail()` in `apps/web/src/server/mail.ts` (SMTP; Mailpit locally). Phase 5 moves sending into the worker.
- Files go to S3-compatible storage via `apps/web/src/server/storage.ts` (RustFS locally — MinIO stopped publishing community images; the API is identical). `apps/web/scripts/storage-init.ts` creates the bucket and makes `avatars/*` and `logos/*` public-read. Validate MIME + magic bytes + size before uploading.
- **Time entries are written only through `apps/web/src/server/time-entries.ts`** (db-injected functions, scoped to one workspace + user). Server actions in `actions/time-entries.ts` wrap it; `createManualEntries` is its one batch path (the CSV import). Later phases add locks and approvals there, so never insert or update `time_entry` anywhere else; the other writers are the rating SQL in `packages/db/src/rates-sql.ts` (the recalculation job and the seed) and the currency relabels in `server/rates.ts`, which change `rate_currency` only.
- **Rates** (`server/rates.ts`, core `rates.ts` and `money.ts`): five levels, most specific first: task, project member, project, member, workspace. Rows are never edited; a change adds a row with `effective_from` (a second change on the same date replaces it), and a null amount means "no rate at this level from this date". An entry is rated when created, with the rate in force at its start; an edit keeps the rate and recomputes the amount; only a change of person, project or task, or billable switched on, re-rates (`needsRerate`). The rate dialog's "New entries only" is effective from today's midnight in the workspace timezone; "Entries from a date" and "All entries" queue the `rate_recalc_job` (`rate-recalc.ts`), run after the response in keyset batches that commit progress and the cursor (Retry resumes; one job per workspace; a new request folds in the waiting job and any failed one: the earliest date, started over; polling `/api/w/[slug]/rate-recalc` fails a job killed mid-run and starts a waiting one nobody runs). `rateEntriesSql` is the only resolution in SQL, tested to agree with core's `resolveRate`. Money: `parseMoney` reads typed amounts as digits (never `parseFloat`), `amountFor` is BigInt half-up, `formatMoney` passes Intl a decimal string. Changing the workspace currency relabels, after a confirmation, the rates and snapshots that follow it (see Cost, profit and currencies). Owners and admins set rates; owners, admins and managers (in their scope) see amounts; members never.
- **Cost, profit and currencies** (Phase 6a; design `docs/superpowers/specs/2026-11-05-phase-6-design.md`): **nothing is ever converted**, and money in two currencies is never added. Cost rates are `rate` rows with `kind = 'cost'` at two levels (project member, then member), always in the workspace currency; `setRate`, `rateHistory`, `currentRate` and `currentRatesAt` take a `kind` (billable when left out). `rateEntriesSql(where, kinds)` writes two snapshots: billable, and cost (`cost_rate_minor`, `cost_rate_source`, `cost_amount_minor`) on every work entry, billable or not; an edit recomputes both amounts, the cost rate changes only with the person or the project (`needsCostRerate`). An entry's currency is its project's client's (`client.currency`), else the workspace's (core `entryCurrency`, `projectCurrency` on the server); a billable rate applies only in its own currency, so project, task and project-member rates are stored in the project's currency and a project billed in another currency is unrated until it has its own rate. Relabels (`relabelWorkspaceCurrency(tx, ws, from, to)`, `relabelProjectsCurrency`) change codes, never numbers, and are the one place outside the entry service and the rating SQL that writes `time_entry` (`rate_currency` only). A project relabel moves the project's own rates and the amounts those rates produced; time rated by a member or workspace rate keeps its number and its currency (₱2,500 never reads as $2,500) until rates are applied to past entries. A rate row in another currency than its target's is never in force (`currentRate`, `currentRatesAt`, the SQL), and `copyProject` copies billable rates only into a project billed in the same currency. `updateClient` and `updateProject` refuse with `CatalogError("CONFIRM")` until `confirmCurrencyChange`, which the actions answer as `fieldErrors.confirmCurrencyChange` and the forms ask through `components/currency-confirm.tsx`. The report engine carries one hidden key, the entry's currency (`coalesce(rate_currency, client.currency)`: a rated amount always shows in the currency it was computed in; an unrated entry follows its project), and `totalsOfRow` folds each row: the workspace currency into `amountMinor`, the rest into `otherAmounts`, cost into `costMinor`, and profit (amount less cost) only over the workspace currency, counting what it leaves out (`profitExcludedCount`) and what has no cost rate (`uncostedCount`). `ReportMoney` is `{ currency, costs }`: `costs` is `report.viewCosts` (owners and admins; managers when `workspace_settings.managers_see_costs`; members never) and everything else reads 0, masked in `maskTotals`; `Viewer.hideCosts` keeps cost off share links and the dashboard. `profitReport` (the Profit tab, `/api/w/[slug]/reports/profit`) is the Summary over one key sorted by profit: 403 from the route, not found as a page; its export always streams, never a job. UI prints money through `components/reports/money-cell.tsx`, one line per currency.
- **Estimates, budgets and alerts** (Phase 6b; core `estimates.ts`, `server/estimates.ts`, `server/budgets.ts`, `server/budget-alerts.ts`): a project has one estimate (`project.estimate_kind` NONE, TIME or MONEY; `estimate_seconds` or `estimate_minor`; `estimate_reset` NONE or MONTHLY; `estimate_alerts`), a task an optional `estimate_seconds` that never adds up into the project's. **Progress is computed, never stored**, by one aggregate, `progressFor` (raw, stopped work entries of the period, no rounding, no scope filter; a money estimate counts only billable amounts rated in the project's currency, `coalesce(client.currency, workspace)`; the period is the workspace's local month, `estimatePeriod`), and reaches every bar (projects list, project header, dashboard top project, Summary rows grouped by project, the Budget tab) through `progressForProjects` / `visibleProgress`, filtered by core `progressVisible`: anyone with `project.update` on the project sees both kinds, everyone else a time bar only when "members see the team's time" is on and a money bar never. `Viewer.hideCosts` (share links, the dashboard's reports) also leaves `SummaryReport.progress` null. `server/estimates.ts` imports nothing from the catalog so `catalog/projects.ts` can import it; `setProjectEstimate` and `getProjectBudget` (the Budget tab: the form, the cumulative chart over the period, the tasks with estimates, `hasRates`) live in `server/budgets.ts` under `project.update`. Alerts: `workspace_settings.budget_thresholds` (up to five whole percents 1–200, `normalizeThresholds`, default 50/80/100); `evaluateBudgets` runs in `runDailyJobs` for every live, estimated project with alerts on and queues one outbox email per threshold crossed, project and period (`kind` `budget:<project>:<threshold>:<period>`) to the active owners and admins and the project's managers; `crossedThresholds` is integer maths (`used * 100 >= t * estimate`). A raised estimate does not re-fire a threshold already sent for the period.
- **Expenses** (Phase 6c; core `expenses.ts`, `server/expenses.ts`, `expense-categories.ts`, `expense-guard.ts`, `expense-receipts.ts`, `expense-report.ts`, `receipts-zip.ts`; the page `/w/[slug]/expenses`, `components/expenses/*`): **always the workspace currency, never converted.** A category is `FIXED` or `UNIT` (unit name + `unit_price_minor`); a UNIT expense stores `quantity_centi` and the price it was priced at (`expenseAmount`, BigInt half up), so a category's price change touches no saved expense. **`expense` is written only by `server/expenses.ts`** (`createExpense`, `updateExpense`, `deleteExpense` soft, `restoreExpense`, `setReceipt`), each under `timerLock` and through `assertExpenseWritable` (`expense-guard.ts`: the entry guard's `assertKeysWritable` over the expense's date key; `expense-writable-coverage.test.ts` fails a writer that skips it): the lock date refuses members and managers, a PENDING or APPROVED period refuses them and asks owners and admins for a `note` (`fieldErrors.note`, `ADMIN_EDIT` with `approval_event.expense_id`). Permissions: `expense.write` is the entries' write row on `{ kind: "entry", userId, projectId }`; `expense.read` is the same shape but a member reads **only their own** (the spec's access table: "members see the team's time" opens time, never money or receipts); `expenseCategory.manage` is admins. The expense dialogs use local state and server `fieldErrors`, not react-hook-form. `expenseScopeFilter(actor)` is the one SQL form of the read rule and `expenseConditions` the one filter (range as local date keys in the viewer's zone, people — a member pinned to themselves —, groups, clients, projects, `categoryIds`, billable) shared by `listExpenses` (keyset on `(date, id)`), `expenseTotalsBy` (the one aggregate: the Expenses report and the Profit tab's expense side, by category, project, person or client) and `buildReceiptsZip`. `expenseScope(db, viewer, id)` is the write scope (`scopeForUser` on the owner; 404 outside), a shared helper for `authorize-coverage`. Receipts: `assertReceipt` types a file by `sniffReceipt` (magic bytes), refusing unknown bytes and an image/PDF disagreement with the declared MIME (a JPEG named `.png` is stored as a JPEG), 4 MB; stored in `S3_EXPORT_BUCKET` under `receipts/<ws>/<expense>` (+ `.thumb.jpg`, made in the browser by `receipt-image.ts`), served by `GET /api/w/[slug]/expenses/[id]/receipt` as a 302 to a 5-minute presigned URL; the receipts zip (`report=receipts&format=zip`) is always an export job. The expense's text is `description`; `note` is the approval note on every write. A submission snapshots `approval_request.expense_count` / `expense_minor` and a project-manager approver manages the expenses' projects too. `profitReport` folds `expenseTotalsBy` into each group (`expenseMinor` a cost, `billableExpenseMinor` revenue; a group with only expenses is appended; a task, tag or description filter leaves them out) and `marginPercent` divides by amount + billable expenses; Summary and Detailed never carry the two fields. `deleteProject` refuses with a message while live expenses exist (`countProjectExpenses`) and purges soft-deleted ones (`purgeDeletedProjectExpenses`); a category's kind cannot change once it has expenses. Expense query keys live under `expenseKeys` (their own prefix); a write also invalidates the reports prefix.
- **Invoices** (Phase 6d; core `invoices.ts`, `server/invoices/*`; the pages `/w/[slug]/invoices` and `/w/[slug]/invoices/[id]`, `components/invoices/*`; the public `/invoice/[token]`): `invoice.manage` is owners and admins (a 404 page, a 403 route otherwise). **`invoice`, `invoice_item`, `payment`, `recurring_invoice`, `invoice_settings` are written only by `server/invoices/*`**; `time_entry.invoice_id` only by `markInvoiced` / `releaseInvoiced` (`time-entries.ts`) and `expense.invoice_id` only by `markExpensesInvoiced` / `releaseExpensesInvoiced` (`expenses.ts`), exempt in the writable-coverage tests. An invoice takes its client's currency when created and keeps it; its number comes from `takeInvoiceNumber` (`SELECT … FOR UPDATE` of `invoice_settings`, skipping numbers already used); stored status is DRAFT, SENT or VOID and the rest is computed by core `invoiceStatus` and `invoiceStatusSql` (nothing owed is PAID, a zero total included; a balance past its due date is OVERDUE, part-paid or not) (tested to agree; it writes `"invoice"."…"` out, so select from the unaliased table). Maths is core `lineAmount`, `percentOf`, `invoiceTotals` (BigInt half up; discount on the subtotal, each tax on subtotal − discount; bps = hundredths of a percent), cached on the row by `recomputeTotals`. The import (`import.ts` `importInto`) selects through the report engine's `invoiceableEntries` (the client's projects, billable, rated in the invoice's currency, `invoiced: "no"`, the workspace rounding rule) under `clientLock` (`pg_advisory_xact_lock(hashtext('invoice:' || client))`), locks its candidate rows `FOR UPDATE` first, and fails unless the marks equal the selection; expenses come only into an invoice in the workspace currency. The guard (`assertKeysWritable`) takes the person's lock, then locks the rows it checks, and refuses any write to an invoiced entry or expense for everyone, note or not (`INVOICED_MESSAGE`), and the editors' reads say "On invoice <n>"; the rate job's `entriesFrom` skips invoiced time; `deleteProject` refuses with invoiced time; `updateClient` refuses a currency change while the client has an invoice that is not void, the workspace settings while an open invoice is in the workspace currency for a client without its own (`hasOpenInvoicesIn`), `updateProject` a move to another client with invoiced time, and `deleteClient` a client with invoices or templates. `sendInvoice` renders `pdf.ts` through `htmlToPdf`, stores `invoices/<ws>/<id>.pdf` in the private bucket, stores the sha256 of a new token (the path is returned once) and, with `email`, enqueues `invoice.sent:<id>` with the outbox's `attachment` — all under the row lock. The public page and its PDF route read no session (`resolvePublicInvoice`: SENT only; `claimInvoiceDownload`: one per 10 s). The daily job (each workspace in its own try/catch) runs `runRecurringInvoices` (one invoice per template and period, `invoice_recurring_period_uq`, catching up the last seven days; a template that fails is reported once per period, `invoice.recurring-failed:<template>:<period>`) and `sendOverdueEmails` (`invoice.overdue:<id>`, once) and returns `invoices: { created, sent, overdue }`. Invoice query keys live under `invoiceKeys`; a write also invalidates the tracker's entries. `sync.ts` is the empty accounting adapter registry.
- **Workspace rules** (Phase 4b; `packages/core/src/workspace-rules.ts`, read by `loadActor` from `workspace_settings` in one query per request): report rounding, hidden pages, who can create, who sees the team's time, required fields, force timer and breaks; every column defaults to the behaviour before the rule existed. A hidden page is a 404 page and a 403 JSON route. Required fields and force timer are enforced in the entry service: `assertRequiredFields` on stop, save, edit, bulk edit and import (a task only when the project has active tasks; breaks exempt); `assertCanWriteTimes` is the matrix's `entry.writeTimes` (manual times refused under force timer for the actor's own entries only; a stop with an explicit end stays allowed). A break (`time_entry.type = 'break'`, `breakAware`) has no details, needs `allow_breaks`, is never rated (`rates-sql.ts` rates work only) and keeps its type; reports count work unless the `type` filter says otherwise; the timesheet grid lists work only.
- **Rounding is a report rule**, never stored on entries: the engine reads it with the currency (`reportSettings`, `ruleFor(query, settings)`), `measures(rule)` sums `roundedSecondsSql` / `roundedAmountSql` (`packages/db/src/rounding-sql.ts`, tested to agree with core `roundDuration`), the URL `rounding=off` shows raw time, the Detailed report sorts by raw duration, and the dashboard asks for raw.
- **Add time for others**: `EntryScope = Viewer & { actedBy?: Actor }`. `scopeForUser(db, viewer, userId)` / `targetScope(ctx, userId)` give the target's own viewer plus the actor after `entry.write`; `scopesForEntries(db, viewer, ids)` resolves the owners of existing entries, so writes take entry ids and creates take a `userId`; a member asking for anyone else is a 404; `writableUsers` lists who the person picker offers. Entry routes take `?userId=`, query keys carry the person (`trackerKeys.entries(slug, userId)`), the tracker, timesheet and calendar read it from `TargetProvider` / `useTarget`, and the timer bar is always the viewer's own.
- **Power features**: bulk edit is all-or-nothing (`bulkUpdateEntries` over the owner groups from `scopesForEntries`); `splitEntry` keeps the rate on both parts; favourites (`favorite_entry`, `server/favorites.ts`) pin details, never times, 20 per person; templates are projects with `is_template` (`listTemplates`, `copyProject` copies tasks, members, groups and rates), hidden from the projects list and the pickers; the Audit tab is the Detailed report with `audit`, `shortMinutes` and `longHours` in the query (`auditConditions`, OR); the CSV import is `POST /api/w/[slug]/time-entries/import` (multipart; `?dryRun=1` plans, the plan's `fingerprint` guards the commit; `server/entry-import.ts`) and writes through `createManualEntries`.
- **Date, time and duration maths only via `packages/core`**: `parseDuration` / `formatDuration` / `formatClock`, `localDateKey`, `zonedDateTimeToInstant`, `addDaysInZone`, `weekBounds`, `formatTimeOfDay`, `parseTimeOfDay`, and `entry-edit.ts` for row edits. They are DST-safe (built on `@date-fns/tz`); never add `n * 86_400_000` to an instant. Viewer preferences come from `resolveViewerPrefs(user, workspaceSettings)`.
- Bare numbers typed as durations are hours (`1.5` = 1:30:00); `1:30`, `90m`, `1h30m` also work.
- **Catalog** (clients, projects, tasks, tags): services in `src/server/catalog/*` take a `Viewer` (`workspaceId`, `userId`, `role`, `actor`) and apply the matrix's `project.view` (admins see everything; others see public projects and private ones they are on, directly or through a group). A private project a member is not on is "not found", never "forbidden". `trackingBlock` says why details cannot take new time (archived project, done task, archived tag); the entry service applies it on start, manual create, continue, duplicate and detail changes. Owners and admins manage the catalog; a project's managers edit their project (not its deletion: `project.delete` is admin-only); the "who can create" setting (Phase 4b) can open creation to managers or everyone. Patch schemas are explicit (`projectPatchSchema`, `clientPatchSchema`, …): zod 4 `.partial()` keeps field defaults, which would reset untouched columns.
- **Tasks by group** (decision 11 of the Phase 4 design, 2026-10-29): `workspace_settings.task_visibility` (`EVERYONE`, the default, or `BY_GROUP`) and the `task_group` table (`task_id`, `group_id`; departments are the existing user groups). `visibleTasksFor(db, viewer, { projectIds?, includeHidden? })` in `server/catalog/tasks.ts` is the one source of member-facing task lists: every active task until the workspace shows tasks by group, then owners and admins all, a manager the tasks of projects they manage plus their groups', a member their groups' only, and a task with no group nobody's. `task-visibility-coverage.test.ts` lists every server module that may read task rows; a new reader fails it. `listPickerProjects` builds its tasks from it and drops a project whose active tasks the person cannot see at all (rule 8). `task.trackTime` is checked in `assertDetailsUsable` wherever a task is assigned, against the entry owner's actor (rule 11: add-for-others, bulk edit and import follow), with `TASK_UNAVAILABLE_MESSAGE`; an entry keeps a task it already has (rule 10), and a split copies it. `assertTaskPicked` is rule 8: on Stop and on saves that touch the project or task, a manager or member on a project with active tasks must pick one (`Task is required.`), never on Start or a time edit. `task.create` and `task.assignGroups` are owner, admin and the project's managers; `setTaskGroups` and `createTask` give a private project's access to the groups in the same transaction (rule 9). With tasks by group a task is never created without a group (the task dialog, the import's "Groups for new tasks"); the picker's inline "Create task" shows only in everyone mode. `Actor.groupIds` is loaded only in `BY_GROUP` mode. `task_assignee` and `task_creators` stay in the schema, unread.
- Pickers: `ProjectPicker` takes and returns `{ projectId, taskId }` (a task implies its project) and shows the entry's own project/task (`current`) when the options no longer list it; the same for `TagPicker` and archived tags.
- Timesheet and calendar read the viewer's entries for a range through `/api/w/[slug]/time-entries/range` under the `trackerKeys.range` key, which sits under the tracker's `entries` prefix, so any entry write (`useEntryWrites`, the list's mutations, another tab) refetches every view. Their maths is pure in `packages/core/src/timesheet.ts` and `calendar.ts`.
- **Reports** (`src/server/reports.ts`): one engine for Summary, Detailed, Weekly, the dashboard, the project Status tab, exports and share links, so their numbers cannot drift. It counts stopped, live entries only, scoped by workspace and by `scopeFilter(actor)` (owners and admins everyone, a manager their scope, a member their own); `effectiveQuery` also pins a member's `userIds` whatever the URL says, and a manager's Users or Groups filter narrows within the scope, never widens it. Amounts (`amountMinor`, `otherAmounts`, `unratedCount`) and `money: { currency, costs }` reach only viewers with `report.viewAmounts`; for everyone else money is null and every amount is zeroed on the server. A share link shows amounts only when made with "Include amounts" and while its creator may still see them. Grouping keys, presets, buckets and sort columns are fixed vocabularies in `packages/core/src/reports.ts`, never strings from the URL. The report query is the URL (`parseReportQuery` / `reportQueryToSearchParams`); filter changes go through the History API, not the router, so no server render runs: `pushState`, so Back undoes a filter, except typed text, which uses `replaceState`. A popover has no exit animation, because Radix keeps a closing popover as the top layer and it would swallow the next Escape. Report data sits under `trackerKeys.report`, inside the tracker's `entries` prefix, so any entry write refetches it. SQL groups by ordinal (`sql.raw("1")`): Drizzle numbers the same parameter differently in SELECT and GROUP BY. Duration sums are `::bigint` with `.mapWith(Number)` (`int` overflows at 2^31 s). The Detailed report pages by keyset on `(sort column, id)` and sums the range on the first page only. Grouping by `tag` repeats a multi-tag entry, so the levels above a tag level take their totals from a second query without the tag join (`groupRows(rows, keys, totals, prefixRows)`). A custom range is a year at most. The Weekly rows choice is the query's `weeklyBy`, so exports and share links follow it. Links into the Detailed report go through core `drillDownQuery` (`lib/report-links.ts`).
- **Exports** read one column record per report (`packages/core/src/report-export.ts`) for CSV (BOM, CRLF) and Excel; the PDF prints a self-contained HTML template in headless Chromium (`report-pdf.ts`). Over `EXPORT_JOB_THRESHOLD` rows (default 10,000) or 4 MB, an export becomes an `export_job` run with `after()` (`runExportJob`, a single call so it can move to pg-boss), stored in the private `S3_EXPORT_BUCKET`, downloaded through a 15-minute presigned URL, and the owner is emailed. Export files never go in the public bucket. CSV text cells that start a formula (`=`, `+`, `-`, `@`, tab, CR) get a leading apostrophe.
- PDF routes need Chromium's binary traced in: `next.config.ts` `outputFileTracingIncludes` keys are globs (`*` for dynamic segments) and the include is the package's real path (pnpm links). A new route that prints a PDF must be added there.
- **Share links** store only the sha256 of a 32-byte token, plus the effective query and the creator's preferences; they read with the creator's current role. Revoked, expired, unknown, or a creator who left: the same 404. The public export allows one download per link every 10 s (`claimShareExport`, 429 otherwise).
- **Approvals and locks** (Phase 5a; `packages/core/src/approvals.ts`, `server/approvals.ts`, `server/approvers.ts`, `server/entry-guard.ts`): periods are the workspace's (its timezone and week start; WEEKLY, SEMI_MONTHLY 1–15/16–end, MONTHLY), inclusive date keys; an entry belongs to the period of its start. `assertWritable` (called only from `time-entries.ts`, every exported writer; `writable-coverage.test.ts` fails otherwise) refuses members' and managers' writes before the lock date and into PENDING or APPROVED periods, and asks owners and admins for a `note` there (`NOTE_REQUIRED` → `fieldErrors.note`), logged as `ADMIN_EDIT`; stopping a timer is never guarded; the lookup ignores `approval_enabled`, so approved time stays read-only after approval is off. Every guarded write and `submitPeriod` take the person's advisory lock (`server/person-lock.ts`). On the client every entry action goes through `withNoteRetry` (`components/approvals/note-prompt.tsx`), which asks once and resends. The editor's reads set `lockedReason` on entries (`listEntriesPage`, `listEditableEntriesInRange`) and the row, cell and calendar turn read-only. The approvers setting is the matrix's `approvers` rule: owners and admins (their own included), then managers for their people, then project managers for periods all on their projects; managers never their own. The rate job skips approved periods and `deleteProject` refuses while submitted time exists (`approval-sql.ts`).
- **Time off and holidays** (Phase 5b; core `time-off.ts`, `holidays.ts`, `server/time-off/*`): time off is never a `time_entry`, never in reports, never rated. Amounts are integer hundredths of the policy's unit (`amount_centi`); balances are computed (`policyBalance`, per calendar year in the workspace timezone, pending counted in `wouldGoNegative`), never stored. `requestTimeOff` counts working days less the person's holidays (`countRequestCenti`) under the person's advisory lock (`timerLock`), via `planRequest` (shared with `previewTimeOff`); review is `timeOff.review` on `{ kind: "approval", userId, projectIds: [] }` (`approversFor(…, "timeOff.review")`, `server/approvers.ts`). A holiday applies through core `holidayApplies` (no assignees = everyone); the dataset import is `@timekeep/core/holiday-import`, imported by server code only (it carries the whole dataset), and `importHolidays` never doubles a (date, name), counting yearly holidays' occurrences. Time off queries live under `timeOffKeys` (their own prefix: entry writes never change them).
- **Attendance and targets** (Phase 5b; core `attendance.ts`, `targets.ts`, `server/attendance.ts`, `server/targets.ts`): days are each person's own (`user.timezone` → workspace), on raw time; capacity is the member's (`membership` daily/weekly minutes, working days) less holidays and approved time off; the people are `attendance.read` (a manager: themselves and the people they manage, not people seen only through projects). `workByPersonDay` is the one aggregate, shared with the daily job's targets. Target emails go once per (rule, person, day or week) through the outbox `kind` `target:<ruleId>:<userId>:<dateKey>`; UNDER honours `user_settings.mute_target_reminders`, OVER never. `runDailyJobs` runs for workspaces with approval on or an active target rule and returns `{ reminders, targets }`.
- **Email outbox** (Phase 5a, `server/outbox.ts`): a cause enqueues its email in its own transaction (`enqueueEmail`, rendered then; `.invalid` stored as SKIPPED); `drainSoon()` (`outbox-after.ts`, `after()`) sends after the response; `drainOutbox` claims due rows with `FOR UPDATE SKIP LOCKED` and a 10-minute lease and retries after 1, 5, 30, 120 minutes. `/api/cron/daily` (Vercel Cron, `vercel.json`, 22:00 UTC) purges old kiosk photos and attempts (`purgeKiosk`), runs `runDailyJobs` (`server/daily-jobs.ts`: the unsubmitted-period reminder, once per person and period), then drains; `/api/cron/outbox` is the local worker's drain. Both need `Authorization: Bearer $CRON_SECRET` and answer 404 without it. `/api/test/run-daily?slug=&now=` runs the daily job for one workspace in e2e (E2E_SECRET; never production; Playwright gives the servers it starts a local secret). Auth and invitation emails are still sent in the request.
- **Kiosks** (Phase 5c; core `kiosk.ts`, `server/kiosk/*`, `server/limited-users.ts`): a kiosk is a device, not a user. `/kiosk/[token]` and the `/api/kiosk/[token]/…` family are authorized by the token alone (`resolveKiosk`; `kiosk-coverage.test.ts` fails a handler that skips it), read no session and set no cookie; only the token's sha256 is stored, so the device URL is shown once, at create and rotate. Unknown, rotated and disabled are the same 404. Identify proves the person by PIN (scrypt, per workspace, `kiosk_credential`) under the advisory lock `kiosk:<kiosk>:<user>`, or by QR (`tkq1.<token>`, sha256 stored, so showing a code issues a new one), and returns an HMAC ticket that lives 120 s and is bound to `token_rotated_at`; a punch re-checks the ticket and that the person is still an allowed active member. Throttles count `kiosk_attempt`: 5 wrong PINs since the last success lock a person on a kiosk for 15 minutes from the fifth (`throttleUntil`), 30 failures pause the kiosk's PIN entry, QR stays open, and successful punches are never limited. **A punch is the entry service** under the person's own viewer (`loadViewer`) at the server's `now`: clock in and end break are `startTimer` with `Kiosk: <name>` and the kiosk's defaults, start break a `break` entry, clock out `stopTimer`, so locks, approvals and required fields apply, and rule 8 means a kiosk on a project with tasks needs a default task; the dialog warns about what the defaults leave unmet (`kioskRequiredGaps`). A kiosk has no way to ask for a note, so an owner's or admin's punch into submitted time is refused with `KIOSK_NEEDS_NOTE`. Limited users are direct `user` inserts, `limited+<id>@kiosk.invalid`, no `account` row, `membership.limited`; Better Auth sends nothing to `.invalid`, `onPasswordReset` verifies the email, and e2e cleanup counts limited members as e2e and deletes the limited members of the workspaces it deletes, never by the `@kiosk.invalid` domain alone: one removed from a customer workspace has no membership and keeps their entries (never add one to the demo tenant). Clock-in photos go only to the private bucket, through a 5-minute presigned URL for `kiosk.manage`, and the daily cron purges them after 90 days and attempts after a day. Personal QR codes and PINs are per workspace, on Profile → Kiosk for workspaces with an active kiosk allowing the person.

A published row is never edited in place: an edit makes or edits the draft that names it (`replaces_id`), a delete makes a tombstone draft; members read `publishedPlanWhere`, planners `workingPlanWhere` (`plan-sql.ts`; every reader uses one of them); `publishSchedule` applies the drafts in the actor's reach (`assignmentScopeFilter` + `assignment.write`) under `pg_advisory_xact_lock(hashtext('schedule:' || ws))` and queues one email per changed person (`schedule.published:<publish>:<user>`) listing their next 28 days. Permissions: `schedule.viewTeam` and `schedule.publish` owners, admins and managers (403 for members); `assignment.write` on `{ kind: "entry", userId, projectId }` (a manager's `scope`, members never); `milestone.manage` the project's managers. An assignment needs a live project the actor can view, a person who can view it ("Add <name> to the project first."), a task the person may track (`visibleTasksFor`), and at least one day to fall on. `readSchedule` is the one read (13 weeks at most): a planner's rows are the people they may write for (a manager: themselves, their people, their projects' members), capacity as Attendance computes it, and hours on a project the viewer cannot see as "Another project" (no id, name, task or note). Schedule queries live under `scheduleKeys` (their own prefix: entry writes never change a plan). **Forecast and Assignments report** (Phase 7b): `publishedPlanDays` (`server/schedule/plan-days.ts`) is the one expansion of the published plan into minutes per person, project and day; `projectForecast` (`server/schedule/forecast.ts`, on `BudgetDTO.forecast`) adds the period's tracked work to the plan from tomorrow, rating each day with core `resolveRate` in the project's currency (a non-billable project or a day with no rate is unrated), and core `forecast` measures the overrun in the estimate's unit with the other unit its share (`proportion`, BigInt half up); `assignmentsReport` (`server/schedule/report.ts`, the Reports › Assignments tab, `/api/w/[slug]/reports/assignments`) sets the plan against raw work on each owner's local day (`assignmentsRows`), members pinned to themselves, invisible projects left out; its export always streams (never a job), and negative durations print with U+2212.

## Deployment (Vercel + Supabase)

- Vercel project `time-keep` (root `apps/web`, region `sin1`), linked to GitHub: every push gets a preview, `main` deploys production. Deployment protection is on; automation uses the bypass secret.
- **One Supabase project holds production and every preview** (tenant = workspace). So:
  - **Previews never migrate.** `scripts/vercel-build.ts` runs `db:migrate` only when `VERCEL_ENV=production`. A schema-changing branch first applies its migrations to the shared database with the **Migrate shared database** workflow (Actions → `migrate.yml` → run on the branch, type `migrate`): the expand step, so the preview can seed and run e2e before the merge, and the production build then has nothing to apply. Until then `pnpm db:seed` refuses to run (pending migrations) rather than half-seed the demo tenant. Test schema changes locally before that.
  - **e2e stays in its own tenants**: `@demo.test` demo users and the `demo` workspace, throwaway `@e2e.test` users. Seeding and `db:e2e-cleanup` only touch workspaces whose members are all such users; never widen that.
  - **`pnpm test` must never point at Supabase**: it truncates every table.
- The app connects through Supavisor in **transaction mode** (port 6543): no named prepared statements, `SET`, `LISTEN/NOTIFY` or session-level advisory locks (transaction-scoped `pg_advisory_xact_lock` is fine). Migrations, seed and cleanup use `DATABASE_URL_SESSION` (port 5432).
- **Every table enables RLS** (`.enableRLS()` on each `pgTable`) and the `anon`/`authenticated` roles have no privileges on `public`, so Supabase's Data API can read nothing. `rls.test.ts` fails if a new table misses it.
- Production and previews set `S3_EXPORT_BUCKET=timekeep-exports` (a private Supabase bucket); previews also set `EXPORT_JOB_THRESHOLD=5`, the value the e2e job test uses (Playwright's local web server sets the same).
- Previews set `MAIL_CAPTURE=true`: email is stored in `captured_email` instead of sent, and the e2e suite reads it from `/api/test/emails` (404 without `E2E_SECRET`, and always in production).
- `.github/workflows/e2e-preview.yml` runs on every successful preview deployment: seed, e2e against the deployment URL, then cleanup.
- **Shared-database safety rules.**
  - Seed and cleanup never delete a demo or e2e user who belongs to a customer workspace: reseeding fails loudly, and cleanup skips that user.
  - Previews capture mail only for `@e2e.test` / `@demo.test` recipients and drop everything else, because preview tokens are valid in production.
  - `test/safe-test-db.ts` refuses any non-local `TEST_DATABASE_URL`.
  - Remote Playwright runs record no traces, because they would capture the bypass header and artifacts are public.
- **Never authorize a Vercel deployment of a fork PR.** Git fork protection is on. An authorized fork build would run with the preview environment, which holds production database credentials, and the e2e workflow would run the fork's code with repository secrets.
- **Migrations must be backward-compatible (expand, then contract).** While a production build runs, live production and every open preview still run old code against the new schema.
- **An index on a large table is built concurrently, by hand, first.** Drizzle runs each migration in a transaction, where `CREATE INDEX CONCURRENTLY` is impossible, and a plain `CREATE INDEX` locks the table against writes while it builds. Before the migration is applied anywhere, change its statement to `CREATE INDEX IF NOT EXISTS` (editing an unapplied migration is fine). Then run `CREATE INDEX CONCURRENTLY IF NOT EXISTS …` with the same name and definition over `DATABASE_URL_SESSION`, and check that it is valid (`pg_index.indisvalid`). The migration then finds the index and does nothing. `time_entry_workspace_start_idx` (0007) was built the plain way while the table was small.

## Working on a phase

1. Read `docs/PRD.md`, `docs/DATA_MODEL.md` and the phase checklist in `docs/PROGRESS.md`.
2. Plan first (folder tree, schema changes, file list), then build part by part.
3. Add a migration with `pnpm db:generate` for every schema change; never edit applied migrations.
4. Finish with `pnpm lint && pnpm typecheck && pnpm test && pnpm e2e`, update `docs/DATA_MODEL.md` and `docs/PROGRESS.md`, update this file if conventions changed, commit, tag.
5. Keep `docs/BACKLOG.md` current: add every deferred finding (review minors, gaps a test run exposed, setup left for later), and move an item to its Done section, with date and commit, in the same commit that fixes it.
